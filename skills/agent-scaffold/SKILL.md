# Agent 生成（SCAFFOLD）

构建项目。骨架来自官方命令；Agent 只写接缝代码；一个确定性门槛决定是否交付。

## 工作流

1. **读输入。**`agent.design.md`（目标、复杂度档位、安全边界、成功标准）与选型决策。缺失或矛盾的输入要退回上游，而不是揣着猜测往前推进。
2. **用官方 CLI 非交互式生成骨架。**用目标技术栈自带的脚手架命令并带全参数（跑 `<cmd> --help` 或读当前官方文档取得非交互 flag——把查到的命令行记录进项目文档供复用）。交互式提示会卡住 Agent：每个提问都要有一个 flag 或 env 默认值应对。
3. **增量接缝能力。**一次接缝一个能力：模型运行时、持久化、可观测、被门控的工具。每个能力经项目自有的薄适配器接入（缝的位置由 `agent-stack` 的选型决策给定）。API 形态不确定时，读已装版本的官方文档——绝不要凭旧 API 的记忆。
4. **接缝期间套用 `security-gates`。**被门控的能力要在同一次变更里带上它的控制。“以后再补控制”会阻塞交付。
5. **验证门槛——确定性的、在交付前：**
   ```bash
   pnpm typecheck && pnpm test && node scripts/validate-env.mjs
   ```
   再加上来自 `security-gates` 的安全检查清单。全部通过才交付：否则修复并重跑。一个无法用命令表达自身成功标准的项目是不完整的——先加命令。
6. **交接**时带一份总结：生成了什么、Agent 写了什么、门槛输出，以及留给 `agent-eval` / `agent-review` 的待办项。

## 纪律

- **源码属于项目。**对这套技能集或任何隐藏框架不得有运行时依赖；生成的一切都是项目可读、自有、可删除的。
- **不要覆盖用户代码。**在既有项目上只做增量改动；破坏性改动走用户批准的 diff。
- **这里不锁版本。**用官方命令安装当前稳定版；lockfile 就是记录。
- 小步走，每次都验证。绝不要批量接缝超过一次失败门槛能解释的改动。

## 交付纪律（standard §12；playbook §3、§5）

构建时就融入这些，让交付的项目可续接、可问责（`playbook` 的项目 harness 与验证部分见 `knowledge/practices/02-harness-and-knowledge.md`、`03-verification-and-safety.md`）：

- **逐步开发**（standard §12.1）：把工作拆成可验证的特性/任务项；一次推进一个或少数几个；会话结束前留一份结构化交接；保持工作区可构建、可读、可继续。绝不在未验证的情况下批量标记任务完成。
- **项目文件骨架**按设计（*.agent/* 树）在第一步就建好——而不是事后清理。用文件、文档、工件就能让一个全新 Agent 续接，绝不依赖聊天记录（playbook §3.3 “换 Agent 检查”）。
- **项目 harness 三件事**（playbook §3）：生成的项目必须能 (1) *读对上下文*（AGENTS.md 是路由器，不是百科全书），(2) 用机械可检查的门槛 *拦截坏输出*，门槛接在交付链上——而不是更强调的指令，以及 (3) *可续接*，一个新 Agent 能按设计描述的状态文件接着做。
- **假修 / 假绿防御**（standard §7.6；playbook §5）：验证必须按一致顺序跑完整套件并引用日志；修复必须能先复现后消除，把原始失败用例作为回归附加，且绝不掩盖（吞异常、放宽断言、跳过测试）。
- **交付链严格门控，判断链宽松**（playbook §3.2）：防止假绿的证据门槛要严格（报告是本轮产出的、测试目录匹配、必跑场景真跑了、没有推到受保护分支）。判断/决策类输出可以明确标注缺口而优雅退化，只要缺口被抛到下游。不要把每个任务都变成僵硬的门槛——但要把那些对误报敏感的门槛做严。
- **完成要对齐外部证据**（standard §8.1）：不能仅凭一次本地的绿色运行就宣告任务完成——代码版本、工作项状态、交付证据必须一致（见 `agent-review`）。
