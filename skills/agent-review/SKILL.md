# Agent 评审（REVIEW）

Agent 工作的就绪度评审。输入：变更（diff 或项目）加它的设计工件。输出：一份发现报告和一个 ship / hold 决定。

## 工作流

1. **加载契约。**`agent.design.md`（复杂度档位、安全边界、成功标准）、选型决策、以及来自 `agent-eval` 的最新评测报告。没有可对照的设计的变更，就按从代码重构出的这些工件当前状态来评审——要明确说出来。
2. **安全审计**走 `security-gates`：diff 里每个被门控的能力都有它的控制，且是 *激活的*（不是“引入了但禁用”）。失败即关闭的语义要验证。Level 3 能力缺控制是自动 MUST-fix 的 hold。
3. **架构漂移检查**走 `complexity-ladder`：代码是否停在合理档位？找悄悄爬升——冒出一个 Agent、引进了工作流引擎、为一百篇文档上了向量库。没有设计修正案的漂移是 MUST-fix。
4. **契约一致性：**发出的事件与记录的事件契约一致；适配器缝仍然隔离着可替换边界；没有技术跨槽位泄漏。
5. **成本评审：**对照设计包络的 token/延迟趋势；提示词压缩或缓存回归标为 SHOULD。
6. **报告发现：**

```markdown
## Review: <范围>
Decision: SHIP | HOLD
MUST (阻塞)：<发现、证据（file:line）、修复方向>
SHOULD (后续)：<发现、证据、建议>
Notes：评测状态、漂移观察、待解决问题
```

## 纪律

- 每个发现都要有证据：文件、行号、命令输出。不要凭感觉。
- 评审不重写代码——它指出问题与方向；修复回到正常流程。
- 评审者的忠诚对象是成功标准，不是 diff 的作者（无论是人还是 Agent）。
- 小 diff、勤评审，胜过大 diff、一次评审。

## 评审纪律（playbook §5；standard §8、§13）

- **只报告可行动的发现**（playbook §5）：只报作者能动手的——具体位置（file:line）与修复方向。跳过风格偏好、假想的未来设计担忧、不可验证的顾虑。评审对准代码与其意图，不去重新翻案已定局的架构。
- **评审意图与权衡，不只是行**（playbook §5）：大变更的交付物带一份意图说明（改了什么、关键权衡及为什么）。在意图层面提问；代码细节交给机械检查。一个意图清晰的大变更胜过意图不明的更小变更。
- **失败 → 工程资产**（standard §8.8）：评审应确认一次失败/事故变成了回归测试或评测，而不仅仅是一行日志。路径是 失败 → 根因 → 纠正措施 → 测试/评测 → 规则/门槛 → 发布 + 回滚。根因修复改变结构，而不只是更大声的提示词。
- **AGENTS.md 作为交付物**（standard §13）：项目的 AGENTS.md 必须回答项目是什么、目录怎么分、允许/禁止什么、常用命令、如何验证、哪些安全边界不可破坏、以及怎么定义“完成”——并且 **不能** 承载完整的架构倾倒、第三方教程或易变的版本清单。评审项目产出一个路由器，而不是百科全书。
- **成本包络评审**（playbook §7）：确认成本在设计包络内；把回归（次优模型路由、每轮重复记账的大 payload、破坏缓存的构建、悄悄删掉行为的提示词压缩）标为 SHOULD 并给具体修复。
- **变更可独立归因**（lessons §6.1）：多起独立变更各自通过单点测试，叠加后仍会呈现为“广泛不一致的退化”。高风险变更（系统提示词、默认参数、缓存策略）要求各自带全套评测与灰度/soak period，且能独立回滚——几起变更捆在一起上，出问题就无法归因。
- **渐进式信任**（playbook §5）：有了稳定的验证循环，人类从验证每个变更退到抽查——但只在循环质量被证实之后。评审应确认最高风险项即使在常规项转向抽查时也保持全量验证。

## 验证门槛——评审这份评审

SHIP 之前确认变更用**独立证据**（不是作者的自称）满足了自己的成功标准：整套真的按顺序跑了、日志被引用、产物存在、没有推到受保护分支、没有掩盖的失败（standard §7.6；playbook §5）。如果某个门槛被跳过或总是绿色，这本身就构成 MUST-fix 的发现。

参考：检查项源自 `doctor` 检查与 catalog `security.requiredControls` 蒸馏（历史实现见归档，不再引用）；标准见 `knowledge/standards/agent-engineering-standard.md` §8、§13；playbook §5。
