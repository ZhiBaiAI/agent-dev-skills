# 复杂度阶梯（COMPLEXITY LADDER）

只有当需求强迫时才向上爬。从最轻的开始，每一档：

1. **确定性函数** —— 无模型。规则、解析、计算。
2. **单次模型调用** —— 一个提示、一个响应、无工具。
3. **结构化调用** —— 单次调用，带 schema 验证的输出。
4. **工具循环** —— 模型调用工具直到完成。大多数 Agent 的默认天花板。
5. **显式工作流** —— 编码好的步骤，每步是一个函数或模型调用。
6. **持久化工作流** —— 状态跨重启存活。需要一个恢复需求。
7. **多智能体** —— 带路由的专门 Agent。需要一个单 Agent 输出无法满足的拓扑需求。

## 规则

- **默认低。**从 1-2 档开始。举证责任在向上爬的一方，从来不在停留的一方。
- **把每一级用文字论证。**“我们需要第 5 档，因为设计文档要求重启后恢复”——一句话，绑到一个需求。含糊的理由（“更稳健”、“面向未来”、“Agent 是大势”）都是拒绝。
- **反默认。**多智能体、RAG、向量库、浏览器、shell、Temporal、Kubernetes 只能通过明确的需求进入，永不作为脚手架默认。每一个也都激活 `security-gates`。
- **复杂度是成本。**每一档都增加故障模式、调试面与评测负担。能满足成功标准的最便宜那一档，才是正确的一档。

## 常见的降档

- 本质是一个任务带步骤的“多智能体”→ 第 5 档工作流。
- <100 篇静态文档的“RAG”→ 确定性搜索或内联上下文。
- 没有恢复需求的“持久化工作流”→ 第 4 档工具循环。

## 每档真正够格的时机（standard §3）

这些是准入测试，不是默认：

- **工具循环**（第 4 档）合适：决策依赖当前环境、成功靠接触真实事物来验证、任务只是少量几次工具调用、模型是自然的路由器。大多数 Agent 在这一档封顶。
- **显式工作流**（第 5 档）合适：顺序已知、不可争辩、稳定；故障模式需要编码恢复；或某个硬步骤不能跳过（如写入前的审批）。固定流水线 = 代码。
- **持久化工作流**（第 6 档）需要真实的**恢复需求**——必须在重启后存活的工作，以及否则会成为灾难的失败。
- **多智能体**（第 7 档）需要一个**单 Agent 无法满足的拓扑需求**——各自独立上下文的不同技能集、独立扩缩、或职责分离。协调是税：每一跳都消耗共享上下文与 token，除非有协调者显式路由，否则一层扁平的平级池往往坍缩成 2-3 个真实干活者（lessons §3.1）。

额外门槛：纯多智能体会放大评测污染（约 3.7× 意外泄露率，lessons §3.3）；持久化执行绝不能在全新的 Temporal 之上手搓持久时长（lessons §4.3）——那是一个持久化框架决策，不是一个代码片段。

## 任务影响驱动评审阶梯（standard §3.8）

先给变更定级，再决定值得做多少阶梯检查：**Minor**（低影响——直接做）、**Standard**（常规——走工作流）、**Major**（架构级——完整设计评审）。简短的任务描述绝不降级一个 Major 的架构选择。复杂度买一送一的成本在 Major 工作上最高，所以那里的文字论证是强制的。

## 成本随档位而不同（playbook §7）

- 子 Agent 默认用更便宜的模型——定义良好的子任务不需要强模型；协调者保留强模型。这是单一最大的成本杠杆。
- 重复/批量工作属于代码编排（一次模型往返、脚本总结），而不是 N 次顺序工具调用。
- 全局缓存稳定前缀（系统提示词、工具定义），会话缓存会话稳定内容，易变内容放最后。
- 优化**整任务成本**，不是单调用成本。一个把任务留在未完成状态的廉价调用是纯浪费；用“任务完成”作为分母来度量 token 消耗。
