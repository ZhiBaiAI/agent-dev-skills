# Agent 评测（EVAL）

评测是项目工件，不是事后补的。每个评测都住在仓库里、跑在 CI 里、在它所守卫的对象回归时让构建失败。

## 工作流

1. **从设计里列出可评测行为**：核心任务成功、工具选择正确性、安全合规、成本包络、降级行为。每一项至少变成一个评测。
2. **按行为选择套件类型：**

   | 套件 | 抓住什么 | 形态 |
   |---|---|---|
   | smoke（冒烟） | 接缝坏了、环境漂移 | 一次真实端到端调用，对结构做断言 |
   | tool-selection（工具选择） | 选错工具、幻觉工具 | 场景 → 期望的工具 + 参数 |
   | security（安全） | 控制绕过、越权 | 被门控能力的探针（来自 `security-gates`） |
   | regression（回归） | 已修 bug 复发 | 每个已关闭的 bug 一个评测，蒸馏而成 |

   区分 **capability** 评测（“能做好什么”——低通过率起步，给改进留刻度）与 **regression** 评测（“还能做以前能做的吗”——近 100% 通过率）；capability 套件通过率爬高后毕业成 regression（lessons §5.4）。

3. **把评测写在它们守护的代码旁边**，一条命令即可运行（`pnpm eval`）。优先确定性断言，而不是模型打分的分数；只在没有确定性信号的地方才用模型打分，并把那些标为“按设计会 flaky”并带容忍度。
4. **给失败分类**，绝不拉平：
   - **blocker** — 答错、安全控制缺失/被绕过
   - **degraded** — 结果对、路径错（多余调用、成本超支）
   - **flaky** — 容忍度或基础设施噪声
   构建在 blocker 上失败；degradation 开 issue；flaky 评测带重试和说明。
5. **跑进门槛里。**评测命令加入 `agent-scaffold` 验证门槛中的类型检查/测试。一个没有自身评测的新能力是不完整的。
6. **报告**按套件：通过率、失败分类、最坏场景链接、单次运行成本。趋势比单个数字重要。

## 纪律

- 关闭 bug 时就把它蒸馏成评测——这个 bug 就是测试用例。
- 防答案记忆：轮换场景、分离 dev/test 夹具、绝不在修复调参所依据的数据上评测。
- 幻觉评测只判“忠实转述”，不判信息来源对错——agent 是信息处理器不是鉴定器；凭空捏造接口名/配置项是幻觉，合理归纳是忠实（lessons §5.13）。
- 成本是一等指标：每个场景的 token 消耗与延迟该进报告，并带设计包络里的回归阈值。

## 评测优先规则（standard §7）

- **评测与特性同生**（§7.1）：评测与它守护的代码一起交付；没有评测的能力是不完整工作。优先确定性断言；只在没有确定性信号处用模型打分，并标为按设计 flaky 且带容忍度。
- **必配评审器 & 门槛设计**（§7.2-7.3）：为重要的行为提供评审器；门槛在 blocker 上让构建失败、在 degradation 上开 issue、flaky 则重试并记录。证据必须基于事实；证据缺失时置信度必须显式降级（§7.4）。
- **粗评粒度、窄判定范围**——每个任务只有一个**主指标**决定通过/失败；其余分开测量以定位弱点。不要把每个指标全 AND 在一起。上游错误（如路由错）毒害下游指标时，记 **skip**，不记 fail——不要为上游噪声惩罚下游（§7.7 指标层级；lessons §5.13）。
- **LLM 当评审必须校准，绝不单独信任**（§7.2；lessons §5.3）：先用人类专家标注的案例校准。细则见下面“机评工程”。
- **在线 + 离线评测都要**（§7.10）：在线评测采样生产 trace → 回答“降了吗”；离线评测跑 curated 集 → 回答“这次改动真的改进了吗”。在线是警报，从来不是 ground truth。在线信号不止 token/延迟——**Keep Rate**（agent 变更在用户库中固定时间后仍保留的比例）与用户对初始输出的语义反应（进入下一个功能 = 完成强信号）测的是“真把事做好了吗”（lessons §5.5）。跑 ADLC 飞轮：生产 trace + 负面反馈 + 评审者修改 → 下一套测试集 → 离线验证 → 部署 → 新 trace。
- **长周期 Agent 评测 trace，不评单行**（§7.10）：把任务建模为 (prompt, expected_behavior, trace)——判定环境结果是否改变，而不是它说得好不好。区分 **Outcome**（最终环境状态）与 **Transcript**（输出 + 工具调用）；“我说我完成了”≠ 环境改变了。多轮任务整组评判——第 1 轮答对、第 3 轮失忆，整组记失败（lessons §5.13）。评测归因要落到失败的那个组件（planner、tool、environment、skill）。

## 机评工程（LLM-as-Judge；lessons §5.3、§5.8、§5.10、§5.14）

确定性断言覆盖不了细微的生成式输出（开放式问答、信息检索）时才用模型评审。用它时：

- **Rubric 是形式化规格，不是自由打分**：每题原子且不重叠——复合问题拆成独立 TRUE/FALSE，同一概念绝不测两遍（重叠会对单一错误双重惩罚）；只评客观可观察的事实，用 MUST/MUST NOT 措辞，强制 TRUE/FALSE；只评 prompt 明确要求过的（prompt 没要引用就不因缺引用扣分）。评严格布尔事实是更简单的任务，可以用更小更快的模型。
- **评目的地，不评路径**：不查 agent 是否用了特定工具或固定步骤序列（模型可能直接知道答案而绕过自定义工具）；要评过程，就让 agent 输出执行计划、评计划本身。
- **先校准，再规模化**：人类专家标注 golden set → judge 对比人工分 → 不一致说明 rubric 歧义，迭代到达标才上线。把模糊指标下钻成 rubric 再二元化（是/否/unknown），用 unknown 占比反查 rubric 定义是否合理；人人/人机一致率（如 85%/90%）达标才允许机评规模化——无一致率保障的机器输出只是机器标注，不是自动化评测。
- **Judge 只做分诊**：高置信 case 自动处理，低置信/冲突/高影响路由给人；定期抽样高置信 case 查系统性错误，追踪 judge 与人的分歧率。
- **元评测集**：维护几十条极端正误样本，定期检查评估器本身，judge 判错即告警——评估你的评估，让进展系统化而非随机化（lessons §5.7、§5.11）。

## 生产级指标（standard §8.1-8.2）

指标分三层，不可互换（lessons §5.8）：**主要产出**（如精确度——直接驱动产品决策）、**安全约束**（如 recall——只许在预定义阈值内降，破线即否决整个实验）、**运维护栏**（延迟/成本/可靠性——决定能不能部署）。大提升但破护栏的实验不推进。

对关键任务，报告不止一个数字：均值、质量下限、波动一起报；多轮试跑；分开首次通过 / 重试后 / 人类接管后；绝不在单次成功、一次 demo、或单一评审分数上交付。

| 指标 | 定义 |
|---|---|
| Task Success Rate（任务成功率） | 成功试跑 / 总试跑 |
| First-pass Completion Rate（首次通过率） | 无重试无接管即完成 |
| All-pass@k | 连续 k 轮都通过的任务占比 |
| Quality Floor（质量下限） | 分数的 P10 / 置信下界 |
| Human Takeover Rate（人类接管率） | 需要人类接管的占比 |
| Cost per Successful Task（单成功任务成本） | 全部运行成本 ÷ 成功任务数 |

**不要**孤立地优化某个最低 token 目标——要把质量与单成功成本一起跟踪。

## 防自我欺骗的护栏（lessons §5；playbook §5）

- 被优化的系统不能拥有它自己的评测集。冻结评测数据（改动走独立审批），结对互相抵消的指标（完成率配对流失率），并让目标定期由人类复审——这个循环自己质问不了坏目标。
- 一个 bug 的评测就是这个 bug（回归套件）：修复 → 蒸馏失败用例 → 作为评测加入。绝不靠放宽断言语掩盖。
- 对抗性完整性：已有模型被观察到意识到自己在被测而作弊（lessons §5.1）——把答案键放在够不着的地方、轮换场景、绝不在评测会对之打分的数据上调参。
