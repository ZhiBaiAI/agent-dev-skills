# Agent 技术选型

为已设计的 Agent 选择技术。输入是一份已接受的 `agent.design.md`；输出是一份选型决策记录，供 scaffold 技能执行。

## 工作流

1. **从设计中提取能力槽位**：模型运行时、API 框架、持久化、队列、可观测、UI 层、部署目标。只取设计确实需要的槽位——不需要的槽位就是被省略的槽位，理由写“不需要”。
2. **逐槽位查阅选型参考**（`knowledge/selection/01-selection-foundations.md` 的三层抽象、确定性谱系、复杂度阶梯）。用框架对照已确认需求得出候选，而不是找“最新最热”。
3. **对每个候选跑两重检查**：
   - `complexity-ladder`：这个技术是否把复杂度推到设计合理档位之上？如果是，拒绝或说服设计变更。
   - `security-gates`：是否触发某个被门控的能力？如果是，其控制进入选型决策。
4. **验证可替换边界。**模型、Agent 运行时、队列、数据库、对象存储、遥测都必须位于项目自己拥有的适配器缝之后。无法隔离在薄接口后面的技术是负债——要标注出来或拒绝。
5. **把每个决策记录为 理由 + 触发 + 替代方案**：

```markdown
| 槽位 | 选择 | 由什么触发 | 为什么拒绝替代方案 |
|---|---|---|---|
| model-runtime | ai-sdk | 流式需求、TS 项目 | 直接 SDK — 没有工具抽象 |
```

6. **资料过时就做实时调研。**如果参考中的版本或 API 形态比生态旧，就查当前主版本的官方文档并记录检索日期。这里绝不锁版本；那是 install 时 scaffold 的职责。

## 纪律

- 每个选中的**和**被省略的组件都带理由。“默认”不是理由。
- 每个可替换边界一个适配器；不允许技术跨两个槽位泄漏。
- 把决策记录到 `agent-scaffold` 和未来评审能找到的地方（目标项目里的 `docs/stack-decisions.md`）。

## 选型原则（standard §4、§11；playbook §7）

选择时应用这些，让技术栈服务于 Agent 纪律而非削弱它（`playbook` 的成本与效率部分见 `knowledge/practices/04-cost-and-rollout.md`）：

- **工具是与确定性系统签的契约，不是免费的方法**（standard §4.1）：每个工具都声明 schema + 允许参数 + 定义良好的输出 + 明确的错误契约。拒绝那些工具无法表达这些的技术。如果一个工具只是没有确定性语义的直接模型调用，优先用 `skill`/提示词，而不是 `tool` 槽位。
- **机械路由走 CLI/MCP，模型路由留在提示词**（standard §4.9）：某个能力如果选择是预先可知、且必须确定性的，就做成 CLI 调用或 MCP 服务器——绝不是每次可能选出不同结果的模型调用。需要确定性的地方选确定性边界；只有真无法用代码表达决策的地方才交给模型。
- **链路 vs 单点模式**（standard §3.7）：流程固定时把槽位 link/chain 成精确工作流；行为多变时保留单点入口。让技术栈形态匹配设计的复杂度档位，而不是某种全槽位最大拓扑。
- **可替换边界不可妥协**（standard §10.2）：模型、Agent 运行时、队列、数据库、对象存储、遥测各居于一个薄的、自有的适配器之后。无法隔离的候选是负债——标注它或拒绝它。优先能分离 Brain / Hands / Session（计算、工具执行、状态）的工具，使三者各自可沙箱化、可独立扩缩。
- **可观测是一等槽位**（standard §9.1）：从 v1 起就记录运行、Agent 步骤、工具调用、检索、护栏、审批、工件；绝不让业务逻辑绑定某个特定可观测平台的数据结构。
- **成本是选型标准**（playbook §7）：定义良好的子任务优先用更便宜的模型，把强模型留给路由器/协调者；批量/重复工作优先用代码编排而不是 N 次模型往返；核算每个已连接服务器的 MCP schema/结果注入成本。
