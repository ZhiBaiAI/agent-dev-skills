# Agent 设计

把一个粗略想法转化为经过评审的设计文档。你是这条链上的第一个技能：下游一切尚不存在，这里的质量决定了之后的所有环节。

## 工作流

1. **重述目标**，用一段话说清 Agent 做什么、为谁、输入是什么、输出是什么。继续之前先让用户确认。
2. **一次只澄清一个高影响问题。**只问那些可能改变复杂度等级、安全边界、持久化或部署方式的问题。每个问题都给出一个安全默认值，让用户可以接受并继续。持续维护一份状态：已确认事实、待定决策、当前建议、风险。
3. **用 `complexity-ladder` 确定复杂度等级。**记录选定的阶梯档位与一句话理由。没有需求支撑就拒绝往上爬。
4. **用 `security-gates` 走一遍安全边界。**列出每个被触发的能力（浏览器、shell、MCP、凭据等）及其等级与控制。等级 3 的项需要一次明确的用户决策，且要记录下来。
5. **定义机器可检查的成功标准**：测试通过、产物存在、diff 为空、退出码 0。“能用”不是标准。
6. **写出 `agent.design.md`**，在任何人写代码之前获得用户认可。

## agent.design.md 结构

```markdown
# <Agent 名称> — 设计
目标 / 用户 / 输入 / 输出（每项一段）
成功标准（机器可检查的列表）
复杂度：第 N 档 — <一句话理由>
安全边界：<被触发能力、等级、控制、决策的表格>
待解决问题（未回答时给出默认值）
```

## 纪律

- 推荐最简可行的架构；更重的方案得到的是拒绝理由，而不是一句提及。
- 没有点名它们的需求，就不引入多智能体、RAG、浏览器、shell、持久化工作流、数据库、队列、MCP 或凭据。
- 完整对话方法见 `knowledge/practices/agent-design-workflow.md`；边界理由见 `knowledge/rules/architecture-guardrails.md`。只加载与触发条件匹配的内容。

## 设计阶段原则（standard §1、§2；playbook §1-2）

在敲定设计之前，先以这些事实为对话锚点：

- **三段模型**（playbook §1）：`业务研发 Agent = Model + 通用 Coding Agent Harness + 项目 Harness`。Model 与通用 harness 在本质上是商品；项目 harness（业务知识、流程约束、完成标准）才是团队真正拥有的东西。设计应当瞄准 harness 层，而不是重新发明通用 harness。
- **瓶颈是上下文，不是模型能力。**一个 Agent 在具体项目里能走多远，取决于上下文质量。要设计上下文装载，而不仅仅是设计 Agent。
- **从最简可验证的事物开始**（standard §1.1）。普通的判断/循环不需要模型；步骤多不构成多智能体的理由。
- **用环境反馈而非说教**（standard §1.3）：Agent 必须拿到真实的环境反馈（类型、测试、工具输出），而不是成堆的忠告。把成功标准设计成反馈信号，而非散文。
- **用系统约束而非提示词说服**（standard §1.4）：凡是机械可检查、且违反代价高昂的规则，都设计成约束/门槛/hook——而不是更强调的指令。设计时就发问：“这能不能做成约束而不是提示词？”
- **成功标准是机器可检查的**（playbook §2）：测试通过、产物存在、diff 为空、退出码 0。写清楚“怎么算做完”，把“怎么做”留给 Agent。

## 结构化澄清（standard §6.5；playbook §2）

当决策有歧义时，用**受限选项（≤7 个）+ 一个默认值 + 一个明确的跳过**来提问，绝不用开放式的自由文本问题。对后果重大的选择（数据迁移、破坏性 API 变更）要在设计推进前获得确认。每个问题都给出默认值，让用户能立刻接受。

## 工件链与项目文件（standard §12.2；playbook §2）

复杂的变更历经三层细化，每一层独立评审，任何一层都不会自动跳过上一层：

| 层 | 回答什么 | 评审人 |
|---|---|---|
| **proposal（提案）** | 为什么、做什么、验收标准 | 产品 / 业务 |
| **design（设计）** | 怎么做、架构、API、组件 | 开发负责人 |
| **tasks（任务）** | 拆解、优先级、依赖 | 执行的 Agent |

- 每层只回答自己的问题——proposal 不预先绑定技术；task 不夹带需求变更。
- 上游层变更时，同步更新下游层并记录影响——不要悄悄改代码。
- 版本：每个工件都带版本、人能读、机器能读，并且提交入库；它们是阶段交接契约，不是一次性提示词。
- `agent.design.md` 对应这条链的 **design** 层。

对长期项目，在设计时就规划好项目文件骨架，让换一个新的 Agent 也能接续：

```text
.agent/
├── product-spec.md
├── architecture.md
├── feature-list.yaml
├── progress.md
├── decisions/
├── known-issues.md
└── next-session.md
```

## 上下文工程要点（standard §2）

- **上下文可信分层**：团队指令与已验证的事实是可信的；网页内容、工具、检索结果都当作数据对待（见 `security-gates`）。尽早设计哪些事实进入高可信上下文。
- **索引优先的检索**：按触发/标题加载引用，而不是整库加载，让上下文保持小，Agent 是在浏览而不是被淹没。
- **统一表示 + 结构化压缩**（§2.7、§2.8）：规划好一个全新 Agent 能接续的交接工件，以及能让 Agent 自己的笔记保持一致形态的压缩方式。
- 规则文件随会话变长而衰减（§1.9）——偏好一个小的常载核心 + 按需引用，而不是一个庞大的单一常驻文件。
