# 5. State、Session、Memory 与耐久执行

## 5.1 区分四类状态

| 概念 | 范围 | 用途 |
|---|---|---|
| Run State | 一次运行 | 当前步骤、预算、中断 |
| Session History | 一个会话 | 消息连续性 |
| Workflow Checkpoint | 一个流程实例 | 恢复、重放、人工暂停 |
| Long-term Memory | 跨会话 | 用户偏好、已验证事实 |

- **MUST NOT** 将四类状态混成一个 messages 数组。
- **MUST NOT** 将业务事实只保存在框架内存中。
- **MUST** 为长期 Memory 定义来源、有效期和删除机制。
- **MUST** 区分模型推断与已验证事实。
- **MUST** Memory 按恢复语义分类管理：工作状态可被新 checkpoint 取代、事件历史追加写、领域知识保留版本与来源、偏好需衰减纠错、凭据留在专用隐私边界——摘要适合压缩上下文，审计依赖原始记录；能无状态完成的任务保持短寿命，持久化本身引入隐私、腐化和迁移成本。
- **MUST** 长期记忆定位为增强能力而非依赖路径：检索失败或超时返回空结果并记 warning，主对话流程继续执行，不阻塞主链路（并行加载时与短期上下文各自独立加载、join 汇合）。
- **SHOULD** 长期记忆注入按 scope 分配 Token 预算（如画像类上限 60%、剩余给任务经验），截断按行进行以保留单条记忆完整语义，避免截断前的估算带入剩余预算计算。
- **SHOULD** 记忆库结构约束导航复杂度：目录层级封顶（如两级，深层级让 AI 定位一条记忆的选择数随深度翻倍；内容增长用文件名前缀消化，不新增层级——想加层级往往是在逃避"这条记忆属于哪类"的判断）；索引先行（总索引 title+description 一行一条 + 目录 README 声明装什么/不装什么，AI 先扫地图再按需读正文）；跨目录主题用 tags 补维度而非目录反复细分；不确定的信息显式标注为"待补齐"而非缺失。
- **MUST** 长任务 Goal 写明 outcome、constraints、verification（Goal 是可执行契约，不是"一直做下去直到完成"）；完成判定由测试、可测指标、Diff、截图、外部状态或人工验收等外部证据确认，**MUST NOT** 以模型自述"已完成"作为完成依据。
- **MUST** 为持续运行定义明确终态（blocked / needs-input / cancelled / budget-exhausted）：verifier 不可达、预算耗尽、权限不足或外部依赖永久失败时进入终态——缺少停止证明和资源上限的 Goal 本质上是无限循环。
- **MUST** 长任务可恢复性以换 Agent 为检验：假设每个阶段结束后换成全新 Agent，仅凭项目内状态、文档与真实工件（非会话历史）能继续推进——Workflow 各阶段规定交接合同（输入来自已确认事实或上一步产物、输出落到文档/代码现场/报告），不能只靠对话记忆；恢复任务（凭持久化信息重建上下文）优先于恢复会话（找回上一段对话）。
- **SHOULD** Harness 组件含对当前模型能力的隐含判断，不是永久资产：新增（Add）与删减（Thin）都由真实任务的运行证据决定（重复失败、缺证据、无法恢复才加；长期无价值、重复实现、频繁误伤则删），只会增加不会减少的 Harness 最终变成新负担。

## 5.2 Checkpoint 与 Store 分离

区分线程级、短期、流程状态的 Checkpointer 与跨线程、长期、应用定义数据的 Store。

- **MUST** 关键运行状态（历史、计数、游标、未处理队列）从第一版就外置到独立存储，进程内不持有分片所需的写权限：单写者进程内状态是水平分片的根因——无状态 worker 追加日志、独立消费者滚动汇总、查询侧读历史的结构才能随负载扩展；进程内单例一旦滞后，下游会拿着过期数据做决策（Anthropic 测试选择服务重构案例：listener 滞后让 selector 决策失效）。
- **MUST** 识别"读写扩展成本不对称"这一事实并据此设计：**读通常好扩，写难得多**——加只读副本会拖慢写，因为每个副本都要参与每次写；而持久化机制往往同时就是扩展机制，改扩展性等于改一致性模型（GitHub 实测：提交量同比涨 5 倍、仓库月请求达十亿级，加副本无法解决写瓶颈，只能重新设计存储与计算的耦合方式，内部基准写吞吐提升 35 倍）。
- **SHOULD** 把协调面压到最小：一次写操作只让**真正需要一致的那一小步**参与仲裁，其余（对象落盘、连通性校验、扫描）并行执行或移出服务路径——写路径上的每一步串行协调都是吞吐上限。
- **SHOULD** 将存储与计算解耦，让读侧按需弹性：读由轻量缓存层承担、权威数据放对象存储，则单点故障的表现是"缓存未命中"而非数据丢失；维护任务（压缩、GC）移到独立 worker，不与服务争资源。
- **SHOULD** 把补丁收益衰减期纳入架构决策：快速修复的续命时间随负载增速递减（加倍机器 70 天 → 按包分片 29 天 → 每日重启不足 1 天），写代码不再是瓶颈时，重设计工期按「人周」估而不是按历史经验估（同一重构一年前约需一季度，AI 辅助下三周完成）。

## 5.3 可恢复 Workflow 规则

耐久运行通过重放到 Checkpoint 恢复。

- **MUST** 将非确定性操作和副作用封装为独立 Task。
- **MUST** 保证 Task 输入输出可序列化。
- **MUST** 让可重试 Task 幂等。
- **MUST** 假设中断前的代码可能再次执行。
- **MUST NOT** 在中断点之前执行无保护的外部副作用。
- **MUST** 明确区分"重跑"与"恢复"：重跑可能走出与中断前不同的路径（模型非确定性），恢复是从已持久化的决策点继续——因此**不能把重跑当作恢复手段**，关键决策必须落盘。
- **SHOULD** 为长跑 Loop 按来源保存处理游标（书签），而非使用固定时间窗：记录每个来源的最新已读时间戳，运行偏早或偏晚时相应伸缩窗口，既不漏处理也不重复处理。
- **MUST** 失败不等于静默：某个来源或依赖不可用时保留其游标、用其余来源继续产出，并在输出中显式标注哪一项未能读取；**跳过的工作必须显式记账，不得计入"干净"**。

## 5.4 执行账本与流式传输

执行账本保存：Run 状态、Step 状态、Event 序列、Checkpoint、Tool 副作用记录、Approval、ArtifactRef、Budget。SSE/WebSocket/轮询负责传输事件，账本负责恢复、审计和状态查询。

- **MUST** 将执行与客户端连接分离。
- **MUST** 为事件分配单调序号和幂等标识。
- **MUST** 支持客户端按 Cursor 续传事件。
- **MUST** 在安全边界写入 Checkpoint。
- **MUST** 将缓存视为性能层，将持久化账本作为恢复依据。

### 异步受理与回调 fence

对外部耗时任务（圈选、生成、批量导入）的工具调用，必须区分「已受理」与「已完成」两个状态；把 `success=true` 当成业务已完成，会让 Agent 结束本轮甚至在下一轮重复提交，而真实任务仍在远端运行。

- **MUST** 在同步阶段只回写受理状态与受理号（如 `createBizId`），**不得写入业务终值**；终值只在回调确认后写入。工具调用成功 ≠ 业务完成 ≠ 页面/结果终值已落。
- **MUST** 将受理号与待完成项一起持久化（不只放在本次 SSE/连接上下文），使回调可以脱离原对话上下文继续推进。
- **MUST** 回调到达时按受理号在待完成账本中定位；命中不到即判定为已过期并丢弃，不得写入。用户可能在等待期间修改了同一位置，新操作会清空旧受理号并登记新指令——写入迟到结果等于覆盖用户当前意图。
- **MUST NOT** 把「等待回调」实现为在轮内轮询；改为结束本轮、由回调触发续跑，前端按在途状态轮询任务结果。
- **MUST NOT** 因超时、本地异常或模型重述而重提已受理的异步副作用任务（会在外部系统创建第二个真实任务）；只有确认未受理才允许重提。
- **MUST** 区分 fence 与锁的职责：Session/Task 锁解决并发读写，CAS 解决状态迁移，fence 解决跨时间结果有效性——三者不可互相替代。
- **SHOULD** 回调只在账本内更新业务事实，不直接驱动任务状态机；阶段推进仍由正常对话编排完成。

## 5.5 Working Memory 与行为资产

运行内信息：Pinned Objective、State、Insights（已验证发现）、Transcript。

跨运行行为资产：Policy（人工审核）、Strategy（Eval/Shadow/回滚）、Action Chain（高频动作序列，按场景召回和版本化）。

- **MUST** 标记 Insights 的来源和验证状态。
- **MUST** 将 Policy、Strategy 和 Action Chain 保存为结构化资产。
- **MUST NOT** 将敏感属性推断写入个人记忆。
- **MUST** 把陈旧记忆本身当作危害对待：过期的状态既可能把已解决的事项重新翻出来，也可能把仍悬而未决的事项压下去——记忆须带失效机制与来源，进入决策前先核对当前真实状态（"一条陈旧的『还在等你』比十条遗漏的信息更伤信任"）。
- **SHOULD** 会话记忆的写入走异步抽取器（会话后离线抽取），不放在对话热路径上同步生成；记忆写路径带验证（抽取结果过校验才入库），防止对话中的临时表述直接污染长期记忆（Anthropic 商务 Agent 记忆异步抽取模式）。
- **MUST** 只为「屏幕上看不到、不写就消失」的东西写记忆：能从当前环境直接读到的状态（余额、坐标、当前页面、此刻的项目状态）写进记忆是冗余的，而且会随环境变化立刻过期，反而拖慢决策。值得记的是策略、计划、验证过的规则与踩过的陷阱——这类内容不写下来就永久消失。判据：这条信息现在能不能从环境重新读到？能，就不要写（Anthropic 记忆实践实测： indiscriminate 写记忆的模型产出 413 个文件仅得 1 个进度徽章，只写 9 个文件的模型得到 4 个）。
- **SHOULD** 让记忆条目自带三个字段：规则本身、**它为什么成立**（怎么验证的）、以及已知的陷阱或反例。只写结论的条目，后续会话无法判断它是否仍适用，也无法在前提变化时修正（实测闭环的模型条目普遍包含 rule + 如何得知为真 + 沿途发现的陷阱，未能闭环的模型只留下零散未验证的猜测）。
- **MUST** 用「回放日志校正记忆」而不是只靠写入时判断：记忆在写入那一刻可能就错了，也可能随环境漂移，而被后续会话原样信任。定期让 Agent 对照原始会话记录复核自己的笔记、修正错误条目——原始记录提供了记忆自身无法提供的 ground truth。少这一环的代价是具体的：一条记错位置关系的笔记会让 Agent 反复走错同一条路，直到任务放弃（Anthropic dreaming 实践）。
- **SHOULD** 记忆容量以「导航需要」而非「记录完整」为目标：用一份顶层索引文件承载当前目标、计划与记忆使用规则，下层按主题分文件；定期合并与裁剪。记忆体系的收益来自可检索性，而非覆盖度——记忆越全，检索成本越高，可用性反而下降。
- **SHOULD** 依赖用户偏好的行为每次重新读取偏好来源，不把偏好烤进提示词或系统指令；偏好来源不可读时停止执行而非使用默认值（默认值会静默违反用户偏好）。
- **SHOULD** 对随时间漂移的偏好类反馈采用带半衰期的时间加权（如半衰期 365 天），避免用陈旧偏好持续训练当前行为。

### 交接等待与流动效率

Agent 把执行时间压到很短之后，交付周期的大头会转移到「轮与轮之间」——产物已交付、接手还没发生。判据不能停在「阶段」，要细化到**轮**：一轮从人的输入开始，到 Agent 交付、人接手给出下一步输入为止。

- **MUST** 按轮核算周期而非只报总数：`周期 = Σ(每轮:Agent 执行时间 + 接手等待) + 外部等待`，并行分支只沿决定完结时刻的关键路径计算、不得各分支相加——只报周期总数就分不清该优化执行侧还是协作侧（实测：编码层人工介入已压到每需求约 0.5 轮，39 个已上线需求四档复杂度的周期仍只缩短一到三成）。
- **SHOULD** 用流动效率做零填报的连续性指标：`流动天 ÷ 流逝天`（当天有任何发言、Agent 回复或工具调用即算在动）。它衡量的是活动连续性，不是有效工时或完成比例，但每天可算、不需要任何人填报，适合做归因分析的起点。
- **MUST** 把静默当作排查入口而非催办判据：发消息前先还原最近一次交接——上一份产物交给了谁、对方还缺什么、有没有新安排。按「对下一步阻碍知道多少」区分**卡点**（已确认具体障碍，如缺权限使验证无法执行）与**悬置**（有交付物但未见接续、也未确认障碍）；只按静默天数触发的模板消息上线即撤回是常见结局（对方已说「下周再看」，系统照常催）。
- **MUST** 区分回执、责任交接与问题解除三种状态：知晓只是回执（还需继续看）、自行接手是责任交接（停止催促）、问题真正解除才关闭（须有证据：材料补齐、明确处理或后续动作证明障碍不在）。计时对象是**这个问题**而非这个群——同一问题被反复提出、被转派者一直没接，而群里其他话题热闹时，只看最后发言时间会漏掉它。
- **MUST** 在报告干预收益前先扣掉自然恢复：实测 261 段静默中「等人回应」占 66%，其中 64% 后来自行恢复活动、恢复时长中位数 3 天。多数等待会自己好，任何「提醒有效」的结论都必须设同期未干预的对照，否则把排期到达与群外完成算成了干预成果。

## 5.6 故障分级与恢复策略

| 级别 | 处理 | 示例 |
|---|---|---|
| RETRY | 当前步骤有界重试 | 超时、限流、暂时网络错误 |
| FALLBACK | 切换替代 Tool/模型/策略 | Provider 异常、检索源不可用 |
| ROLLBACK | 回到最近稳定 Checkpoint | Gate 失败、产物不合格 |
| NEED_INPUT | 暂停并请求用户信息 | 关键需求缺失、业务取舍 |
| ABORT | 终止并保留证据 | 权限失败、数据完整性风险 |

- **MUST** 为每个错误码定义默认恢复级别。
- **MUST** 限制重试次数、总时长和成本。
- **MUST** 避免对确定性错误执行原样重试。
- **MUST** 在回退前确认副作用状态。
- **SHOULD** 把超时归类为"未知"而非"失败"：服务端可能已成功但客户端报错，超时类错误不自动重试——先用请求 ID 做状态查询确认副作用真实状态（成功/失败/在途），未知状态清空前禁止重复发起同 ID 的副作用调用（TikTok SRE：超时=未知，退款案例盲目重试=双倍退款）。
- **SHOULD** 为外部依赖配置熔断器与扇出上限：下游持续失败时熔断阻止 Agent 继续调用（保护下游、防级联故障）；Agent 重试与并行调用设最大并行度，配合指数退避——幂等只防重复副作用，不防重试风暴（TikTok SRE 分布式系统模式）。

## 5.7 知识资产分层

| 类型 | 内容 | 主要治理 |
|---|---|---|
| Domain Knowledge | 业务事实、术语、指标、元数据、实体关系 | 来源、Owner、有效期、权限 |
| Behavior Spec | Agent 与交付物的行为和质量规则 | Rule ID、版本、Gate、Eval |
| Workflow Config | 阶段、状态、路由、重试、审批和恢复 | 依赖检查、发布、回滚 |
| Skill / Capability | 可执行能力及资源 | 版本、权限、Contract |
| Experience | 经真实运行验证的行动方法 | 证据、范围、衰减、回滚 |

- **MUST** 分别版本化 Domain Knowledge、Behavior Spec 和 Workflow Config。
- **MUST** 区分事实、规则、流程和经验。
- **MUST NOT** 将行为规则存入领域事实库。
- **MUST NOT** 将工作流顺序仅写入 Prompt。
- **MUST** 规则与补丁归资源拥有方：某系统的内部规则由该系统团队维护，Agent 不复制拥有方内部规则、不替拥有方打补丁；对资源状态的确认（是否真的关闭、是否真的生效）由拥有资源的系统出证据。补丁堆进 Agent 会让错误边界维持得更久——每次修得更快，根一直没动。
- **MUST** 让代码事实只由代码索引回答，不抄进文档、不写进记忆：文档里写"某函数在某文件"这类事实，一次重构就会过期，而 agent 读到过时信息比读不到更糟。代码结构交由图谱或符号索引回答，文档只承载"为什么"。
- **MUST** 把「选错、用错、口径对不上」这类静默错误当作知识缺口来治，而不是换更强模型：有一类失败没有任何报错——代码能跑、查询能返回、格式合规，但结果就是不对（选错表、同名字段含义不同、指标口径约定只存在于历史代码里）。实测换更强模型能提升选表与语法稳定性，口径偏差依旧，因为**从未出现在上下文里的业务约定，任何模型都拿不到**。治法是把隐性业务知识结构化：为同一业务概念绑定它在该域下的具体字段与枚举（消除歧义）、把散落在历史代码里的 CASE WHEN 与映射表显式化（补全规则）、让每次人工修正与 bad case 回流（可迭代）。产物应是机器可校验的结构化三元组，而非自然语言描述——自然语言无法判断是否仍与线上代码一致。

## 5.7.1 编译而非检索：知识库要在检索前先加工

RAG 并不改变原始材料的状态：散落的还是散落的、矛盾的还是矛盾的、过期的还是过期的，只是多了一层向量索引——于是问题从「人找不到」变成「AI 找到了但答不准」。**问题出在知识本身，不在检索**。因此需要在检索之前加一道编译：把源材料预先加工成有结构、有约束、可校验的知识资产（直播数据 LLM Wiki 实践）。

- **MUST** 让目录承担状态语义，而不是用状态字段描述状态：`pre/`（待处理清单与临时下载）→ `raw/ready|pending|archive/`（原始材料按可编译性分流）→ `wiki/`（编译产物），再加 `log/`（构建与体检报告）、`tmp/`（跨 Skill 协作中间态）、`schema/`（页面契约模板）。生成阶段只读 `ready/`，等于把「材料能不能用」从隐藏字段变成目录归属的物理事实——低质量材料在入口就被挡住，不会流进编译流水线。
- **MUST** 把页面结构固定成 Schema 契约，并让所有环节共用同一个解析器：生成器按它写、图构建器按它提取关系、健康检查按它校验、检索按它读。否则生成器写了检查器读不出的结构，两边的「同一份知识」已经不是一份。实现上是 frontmatter（结构化字段，承载血缘、归属、消费关系，脚本可直接按字段提取）+ 正文（Markdown，承载业务背景与加工口径供模型理解），再配 `[[页面名]]` 级别的弱引用兜底，把正文里提到但没落到字段的关系也扫进图。
- **MUST** 把生成与判断分离：需要推断的字段（如域归属）在生成阶段一律留空，等所有基础页面落盘后再独立跑一轮基于全局信息的判断，输出候选交人确认后回填。让模型在只掌握局部材料时做全局判断，它给出的只是看起来合理的猜测。
- **MUST** 只存正向边、按需反查、回填关键反向字段：正向边与反向边互为冗余，存两份必然要维护双向一致性。关系图只存正向边（存储减半、一致性问题消失），运行时按需建索引；同时把高频的反向查询结果（如每张表的下游列表）回填到页面 frontmatter，让只读单页的轻量消费方不必加载整张图。
- **MUST** 让增量编译以「对账」而不是「时间窗口」判断变化：每次构建前比对三方状态——源材料目录的新增/删除/内容变化、已有页面集合、页面 `sources` 字段记录的来源。差异决定这次只重跑哪些阶段的子集，把构建成本从「与总量相关」变成「与变化量相关」。同一套检查提升为周期性 Lint 后，知识库的健康度就从「构建时合格」变成「持续合格」。
- **SHOULD** 用「结构化产出 + 确定性脚本兜底 + 人守边界」的三层分工：抓取、对账、校验、分流这类判断性低的任务全脚本化（可重放、不耗 token、无幻觉）；页面生成与归并这类需要理解的任务交模型；域归属、指标合并这类机器不该独断的决策嵌进编排节点等人工确认，而不是事后打补丁。
- **SHOULD** 让检索侧按查询类型分流而不是一律走向量检索：实体名明确的精确查询直接读页面与血缘；带方向词的关系查询走图遍历；只有模糊搜索才走「域推断收敛范围 → 关键词与域两路召回 → 图扩展补血缘 → 粗排定候选 → 精排逐页读详情」的完整链路。精排要有一条硬约束——**每张候选都必须读详情，不允许前几张匹配度高就提前停止**，靠后的表可能因为覆盖更全、被更多下游消费而成为更优推荐。
- **MUST** 把「读到知识」与「核实了实现」当成两个不同的完成条件，并在消费协议里显式分开：知识只保存**结构与定位信息**（接口、类、字段、配置项的标识与路径），当前事实必须在任务执行时回源确认。消费分五步——发现域 → 选择场景（完整读边界，不拿摘要替代）→ 按需求选链 → 展开必要依赖 → **回源核验**（逐项建立「导航断言—当前事实—核验结论」的对应关系）。三条纪律：命中重复或未命中时结束扩展并**报告缺口**；来源不可达或定位符失效时**不把「查不到」推断成「没有影响」**；**知识在任务内只读**，任务中的推测不得直接写回共享知识（淘宝直播互动团队 LiveX Wiki 实践）。
- **MUST** 让知识承载业务结构而不是条目堆积：以「业务场景」为知识单元、域明确归属、共享知识被引用而非复制，并在场景内部沿「真实接口 → 服务编排 → 核心模块 → 底部依赖」建立查证路径——按仓库或技术主题自动分组，只会让 Agent 在每个任务里临时重建关系。这条有量化支撑：同批次对照下，按场景组织的知识库端到端生码得分较无知识库相对提升约 39.15%、较 RAG 向量库提升约 30.1%，链路定位 F1 达 1.38（同类任务基准为 1.00，两批评测分别提升 54.5%/23.8% 与 44.3%/15.9%，均为批次内相对值而非绝对值）。
- **SHOULD** 用「知识自审查」补 diff 追踪的盲区：只沿已有定位符追代码变更，会长期发现不了地图之外的链路；因此定期（而非仅在有提交时）回到源码与平台核对已记录的接口与依赖，并**重新枚举入口、注册点、调用方与策略实现**以找遗漏。近期没有代码提交的场景也要查，因为运行控制仍可能变化。

## 5.8 知识冷启动

流程：代码/Schema/文档/历史 SQL/接口/评审记录 → 自动抽取候选 → 去重与冲突检测 → 来源绑定 → 领域审核 → Eval → 发布。

- **MUST** 将自动抽取结果标记为 CANDIDATE。
- **MUST** 对公式、权限、业务口径和隐含条件进行人工审核。
- **MUST NOT** 因抽取置信度高自动发布关键业务事实。

## 5.8.1 知识变更的治理链：谁确认过，比写了什么更重要

光把口径写下来不够。定义**有没有被确认过、变更有没有被留住、查询跟不跟得上**，这三件才决定它能不能被 agent 当真使用。人遇到口径歧义可以问一句「这次按支付时间算」，agent 没有这个渠道——它拿到一列数字，无法知道来自哪个指标、哪个版本、谁确认过。所以治理链要把「谁确认过」嵌进主链路，而不只是写在规范里（淘宝闪购本体平台实践）：

- **MUST** 维持**单向派生**：生效的定义只存一份唯一事实源，图库、倒排索引、向量索引全是派生物，随时可从事实源重建。反过来把读模型当源头用，改名、合并、回滚就得同时改多处；两边对不上时没有第三方能判断谁对。
- **MUST** 拆分「产出候选」与「判定对错」两个模块，不能合并：一旦挖掘模块知道自己产出的东西马上要被同一套规则卡住，它就会开始自我审查、只抽肯定能过的，覆盖面先垮掉。同理，「范围」（场景）与「形态」（接口）也不能混——把范围塞进接口会长出一堆业务参数，把形态塞进场景会退化成固定查询模板。
- **MUST** 在草稿提交前查重，而不是发布后再合并：把已发布定义与在途草稿放在一起，按标识与名称双向比对。发布后才发现是同一对象，成本极高且脏数据已流入下游。
- **MUST** 让确认记录绑定「本次变更最终生效的那个版本」，而不是草稿编号——绑错则确认挂在错误版本上，事后无法追溯到底确认了什么。
- **MUST** 先落审批记录再启动流程：顺序颠倒时流程启动成功而记录写入失败，会产生一张找不到对应变更的审批单，只能人工清理。记录写失败就直接终止。
- **MUST** 发布前做**三方比对**（线上值 / 草稿值 / 基线值）：三方一致直接放行，仅草稿变更取草稿，线上与草稿均变更且不一致则列出冲突交人裁决，**绝不静默覆盖任何一侧**。并发场景下，字段级合并是唯一能清晰界定「改动意图归属」的手段。
- **MUST** 让状态只由回调推进，并对未回调的单据定期对账、对停滞在中间态的执行补偿；对账与补偿必须幂等——重试多少次，版本号只递增一次。
- **MUST** 分离稳定标识与外部标识：稳定标识终身不变、外部标识可改。改名只更新外部标识，引用方无需重写，避免改名把关系、场景与接口说明全部打断。
- **SHOULD** 设一个等待上限：领域 owner 精力有限，未确认单据要定期自动催办，而不是无限期悬着（实测累计处理 1477 张确认单、平均 3 个自然日闭环）。

## 5.9 知识持续回流

回流来源：用户纠正、Gate 失败、代码评审、真实环境验证、生产 Incident、冒烟与回归 Eval、Tool 与 Schema 变更。

- **MUST** 将纠正记录为候选变更。
- **MUST** 区分领域事实错误、行为规则缺失和工作流配置错误。
- **MUST** 为知识变更新增或更新回归 Eval。
- **MUST NOT** 将用户单次表述直接覆盖共享知识。
- **MUST** 为知识条目埋点记录实际被读取的次数与最近读取时间，用数据而非感觉决定淘汰：借工具钩子统计命中（同一条目短时间窗口内只计一次，钩子异常必须静默退出、不影响主流程），定期输出命中排行与从未被读的"僵尸条目"——过时的删、有用但检索不到的补关键词、常命中的补充完善或晋升。
- **SHOULD** 让知识按"记忆 → 文档 → 规则"单向晋升，而不是直接写成规则：一条经验反复验证成为稳定约定后晋升进文档并删除原条目；同类问题反复出现说明记忆没防住，才考虑升级为规则。规则每次会话都加载、每多一条就稀释其他规则，而记忆按需检索、没命中时不占注意力（实测：一次全量审计把 148 条记忆精简到 24 条；13 条进化记录里只有 3 条升级为规则）。
- **MUST NOT** 让 agent 自行修改规则：进化记录先进待审阅区，由负责人逐条决定升级为规则、沉淀为记忆还是拒绝。

## 5.9.1 知识工厂：让「干活」自己暴露缺什么知识

知识维护最常见的死法是把「先写完所有文档」当成前置条件——永远写不完，也与实际任务脱节。可运转的做法反过来：**让做事的过程暴露缺什么，补上缺口让下一次做得更好**（LangChain 知识工厂实践）。

维护的知识分三类，来源与更新节奏各不相同：

| 类别 | 内容 | 更新特征 |
|---|---|---|
| 技能（怎么做） | 按组织要求完成任务的流程、指令与脚本，常年在同事之间口口相传、从未写下来 | 随做法演进，最该补齐 |
| 领域知识（业务是什么） | 产品、客户、竞品、组织的定义与事实 | 不常失效，但天然不完整或有错 |
| 数据访问指引（去哪儿取） | 数据在哪、该信哪个来源、怎么查 | 源头已可靠时**不要另存副本**，只维护「怎么取」 |

支撑这三类知识的不是人肉维护，而是三个组件：

- **MUST** 给 Agent 一个「上报知识缺口」的工具：当它找不到信息、或发现信息是错的，能上报并可选给出修正建议。这是发现缺口最便宜也最准的渠道——只靠人回想去补，永远补不到 Agent 真正卡住的地方。
- **MUST** 由独立的 **curator Agent** 定期维护知识，而不是让使用知识的 Agent 顺手改：使用方擅长发现「哪里错/缺」，但改对需要理解底层知识与其他数据源；让只顾自己目标的 Agent 去改共享知识，结果必然是互相矛盾、越改越乱。curator 需要能读全部原始来源（文档库、聊天记录）、能读 Agent trace（从中看出人是怎么用 Agent 的、把过程固化成技能），以及上面那份缺口清单。
- **SHOULD** 把**存储格式当次要问题**：技能可以放 Git、放单文件、放知识图谱——curator 只要能跟这些格式交互即可。当前真正没有标准的是「语义记忆」该长什么样，过早规定格式反而增加负担。
- **MUST** 由 trace 捕获「人机往返中产生的知识」：报告生成后财务负责人同步改了几处格式并说明今后统一用新标题——这段往返本身就是知识，curator 当夜读 trace 时应把它写进对应的技能里。**知识不只来自文档，也来自纠正的那一刻。**

落地顺序建议从一条反复出现的工作流开始，观察 Agent 在哪里卡住，先把那个环闭上，而不是先建一张全覆盖的知识地图。

## 5.10 知识过时与冲突治理

知识条目应包含：Owner、来源、有效时间、最后验证时间、消费次数、失败关联次数、依赖资产、替代条目。

触发重新验证：来源变化、Tool/Schema/接口升级、关联任务连续失败、多来源冲突、超期、长期未使用但仍 Active。

- **SHOULD** 用定期巡检把「保鲜」做成自动动作，而不是靠人记得：每天跑一次全量比对，逐篇把知识条目与代码/系统现状对照，找出过时段落、失真章节与失效结论；偏差自动生成修复提案，走与入库相同的准入门禁（AI 预审 + 评测集回归 + 人工确认），合入即完成一轮保鲜。另配一套按模块出题的评测集持续「考试」，用答题结果度量保鲜度与准确率——只靠人工发现的过期知识，一定晚于它造成的误导（支付宝大促知识库实践）。

- **MUST** 在冲突未解决时向运行时返回冲突状态。
- **MUST** 阻止高风险任务使用 SUSPECT 知识。
- **MUST** 记录采用哪一版本知识生成了结果。
- **SHOULD** 把「wiki 式互链结构」当作大规模知识库的导航层，而不是只靠扁平检索：由 Agent 自己在空闲期（dreaming）逐页编写与维护主题页、互相链接、合并重复、核对来源；检索工具负责找到入口，wiki 负责给出主题间的关联路径。实测两件事都做时收益明显高于只做检索——同一批 350,000 个文件、约 4.2 亿 token 的语料，答案落在多文档交叉的问题上，查 wiki 得分 87%、只用检索 73%；随会话累积（2 → 128 轮），wiki 覆盖让评分从 13% 升到 48%，配合检索时从 54% 升到 61%，且每题约省 2 万 token。判据不是「文档全不全」，而是**跨文档的关联能不能被直接走通**（Anthropic 记忆实践）。

## 5.11 Loop State

- **MUST** 将发现 Cursor、去重键、工作项状态和验证证据持久化。
- **MUST** 使用 Claim Lease 防止多个 Worker 重复处理同一工作项。
- **MUST** 支持崩溃恢复、Lease 过期回收和幂等重放。
- **MUST** 下一轮 prompt 显式要求先读状态文件、按状态决定是否继续——只写不读的状态文件是一份没人看的日报。
- **MUST** 让进度只能经命令推进、不能由 Agent 直接改写：状态落文件，但每次转移必须过 CLI 或同等确定性入口，并用 Hook 守卫拦截对状态文件的直接写入——否则 Agent 会悄悄标记"已完成"跳过步骤，事后从产物上看不出少了哪一步。同一份执行记录（每步完成时间、触发者、产出报告）同时用于冷启动恢复与事后审计。

### 5.11.1 常驻 Agent 的五个原语

「常驻」（always-on）描述的是用户体验，不是运行状态：Agent 绝大部分时间在睡，周期性醒来做一次 run，做完再睡。要让它可靠地这么循环，需要五个各自独立的组件——把它们混在一起（例如让每个事件源直接调用 Agent）会同时带来竞态与丢事件两类故障。

- **MUST** 用**事件收件箱**承接所有触发，而不是让每个来源直接调 Agent：持久事件表 + 写入端点 + 后台 worker 三段式，事件带状态、按来源唯一标识去重。三条纪律：端点要快速回执（部分 webhook 提供方把慢响应判为失败，深度校验放到 run 内做）；收件箱是唯一事实来源（worker 被唤醒先拉最新事件，死了也能被新 worker 接上重试）；同一收件箱同时只有一个活跃 worker（避免两个 run 重复做功或互相覆盖）。run 进行中来了新事件，可选择推到下一轮、并入当前轮、或打断重启。
- **MUST** 把**定时器**放在独立存储，不混进收件箱——收件箱只存放"现在可处理"的事件。定时器分两类：**跟进**（Agent 给自己设的截止时间，触发后标记完成）与**周期**（按固定节奏重复，触发后把到期时间推到下一次）。定时器自身不发起 run，由调度器轮询到期项、更新状态、再往收件箱投一条事件。
- **MUST** 让**记忆**指向持久存储而非 worker 本地，并只存「查不回来的东西」：用户指令（每轮开始时加载，用户不在场时要靠它延续）、关于用户的笔记（先单文件，增长后拆多文件 + 只加载索引）、已说过的内容（避免重复告知）、任务进度（新 run 据此接着做）。已在其他系统里的事实存指针即可。
- **MUST** 把**权限**当作常驻 Agent 风险最高的部分单独设计：run 持有用户权限且无人值守，每个工具调用都要能判定「自己继续 / 阻塞 / 等批准」。凭证走环境外代理注入；高风险动作由分类器拦截；需要澄清或批准时用**延迟工具调用**——run 结束、会话中途保存，请求以卡片形式给用户，用户答复作为新事件回到收件箱并恢复会话。等待期间 worker 可处理其他事件，Agent 不被阻塞。
- **SHOULD** 用**发件箱**控制对外消息的节奏与投递可靠性：run 的结束方式只有三种——发一条消息、判定无需发送、或发起延迟工具调用请求批准。多数场景一个「发送」工具就够，只有在需要对消息限速或从投递失败中恢复时才需要独立发件箱（待发消息表 + 分发器）。消息量要能用评测调出平衡：发太多成为噪音，发太少漏掉用户需要知道的；**实践中更好的策略是先安静、再逐步赢得用户注意力**。

## 5.12 Thread 与 Run 并发

策略：QUEUE（顺序）、REJECT（冲突）、CANCEL_PREVIOUS、FORK（分叉并行）、OPTIMISTIC（乐观锁）。

- **MUST** 在创建 Run 时返回排队、冲突、取消或分叉结果。
- **MUST** 让消息、Event、Artifact、Workspace 和副作用归属具体 Run。
- **MUST** 防止并发 Run 写入同名 Artifact 或同一外部资源。

## 5.13 Checkpoint Schema 演进

- **MUST** 为 Checkpoint 保存 Schema 和 Runtime 版本。
- **MUST** 为可恢复版本提供迁移函数。
- **MUST** 定义兼容窗口和历史恢复期限。
- **MUST NOT** 静默丢弃旧字段或待处理副作用。

## 5.14 Interrupt 与 Resume

- **MUST** 在中断前持久化 Checkpoint。
- **MUST** 对中断载荷和恢复输入使用 Schema。
- **MUST** 校验恢复者身份、权限、状态版本和过期时间。
- **MUST** 保证重复 Resume 不造成重复副作用。
- **MUST** 在恢复后重新执行适用 Guardrail。
- **MUST NOT** 依赖进程内同步等待实现长时间审批。
- **MUST** 持久化 Goal 状态与进程内激活状态分离：进程重启后持久 active 的 Goal 默认不自动唤醒（需显式重新激活），防止恢复瞬间唤醒全部历史任务；Round 超限、max-tokens、Agent 错误等异常一律先去激活，状态说不清时先停止而非盲目重试。
- **MUST NOT** 解析并执行因 token 上限被截断的响应中的工具调用——半截 JSON 即使被解析器补全、schema 校验通过，参数语义也可能已经改变（写操作副作用落地后不可收回）；应终止本轮交上层决定，或以错误结果交回模型重新发起调用。
