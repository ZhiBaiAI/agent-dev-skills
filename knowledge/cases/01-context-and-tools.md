## 1. Context / Prompt 工程

### 1.1 缓存优化 bug 导致"持续性失忆"——Anthropic 真实生产事故

- **来源：** [Anthropic — An update on recent Claude Code quality reports (April 23 Postmortem)](https://www.anthropic.com/engineering/april-23-postmortem) ｜ 2026-04-23
- **问题：** Claude Code 用户大量报告"模型变笨了"——遗忘、重复、工具调用诡异，且用量额度异常快速消耗。最终定位为三起独立变更叠加，其中最严重的是缓存优化 bug。
- **原因：** 3 月 26 日上线一个"会话闲置超 1 小时则清理旧 thinking 以降低恢复成本"的优化，本应只清一次，实际变成会话剩余每一轮都清。一旦会话跨过闲置阈值，后续每次请求都只保留最近一个 reasoning block，Claude 越跑越不知道自己为何做这些编辑/工具调用。被清理的 thinking 还导致每次都 cache miss，额度飞涨。该 bug 躲过了人工 review、单测、e2e 测试、自动化验证和 dogfooding——因为它只在"陈旧会话"边界条件下触发，且两个不相关实验恰好掩盖了它。
- **解决方法：** 修复 bug；用 Opus 4.7 对涉事 PR 回溯跑 Code Review（4.6 不能）；收紧 system prompt 变更流程——每次 prompt 改动跑全套 per-model eval + 持续 ablation（逐行删 prompt 看影响）+ 新建 prompt 变更审计工具 + CLAUDE.md 加引导让模型相关改动只 gate 到对应模型；任何可能牺牲智能的改动增加 soak period + 更广 eval + 灰度。

### 1.2 单行 system prompt 让编码质量掉 3%——"减少冗长"的反作用

- **来源：** 同上（April 23 Postmortem）
- **问题：** Opus 4.7 倾向冗长，团队在 system prompt 加了一句 `Length limits: keep text between tool calls to ≤25 words. Keep final responses to ≤100 words unless the task requires more detail.`，内部多周测试无回归，4 月 16 日随 Opus 4.7 上线后编码质量下降。
- **原因：** 内部 eval 集不够广，没覆盖到受影响的场景。事后用更广 eval 集 ablation 才发现这一行让 Opus 4.6 和 4.7 各掉 3%。
- **解决方法：** 回滚该 prompt；确立"每次 system prompt 改动跑全套 per-model eval + 持续 ablation"流程。

### 1.3 "上下文焦虑"——模型接近上下文上限时提前摆烂

- **来源：** [Anthropic — Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps) ｜ 2026-03-24（[Scaling Managed Agents](https://www.anthropic.com/engineering/managed-agents) 同样提及）
- **问题：** Claude Sonnet 4.5 在长任务中，上下文窗口快满时会"提前收尾"——草率结束工作，即使任务没做完。称为 "context anxiety"。
- **原因：** 模型感知到上下文将满，倾向于主动 wrap up 而非继续推进。compaction（就地摘要历史）不能解决，因为没给模型"干净的开始"，焦虑仍在。
- **解决方法：** 用 context reset——完全清空上下文窗口启动新 agent，配合结构化 handoff artifact 把上一个 agent 的状态和下一步任务传过去。这是当时长任务 harness 的关键 unlock。但 Opus 4.5 自身消除了该行为，reset 反而变成 dead weight——说明 harness 里编码的假设会随模型升级而过时，需持续质疑。

### 1.4 会话中途切模型 → 缓存全失效 + 工具集不匹配

- **来源：** [Cursor — 持续改进我们的智能体框架](https://cursor.com/cn/blog/continually-improving-agent-harness) ｜ 2026-04-30
- **问题：** 用户在对话中途切换模型时，缓存是 provider/model 特定的——切换即 cache miss，第一轮又慢又贵；且新模型要把工具应用到"由别的模型生成的对话历史"上，历史不在其训练分布内，行为异常。
- **原因：** 不同模型行为/提示/工具接口形式不同（OpenAI 用 patch 格式编辑文件，Anthropic 用字符串替换）；切换后新模型可能调用历史中出现但不属于自己工具集的工具。
- **解决方法：** 切换时自动切到对应模型定制的 prompt + 工具集，加自定义指令告诉模型"你是在聊天中途从另一模型接管"，引导它别调用不属于自己的工具；除非有明确理由否则整段对话保持同模型；更好的办法是改用 subagent（全新上下文窗口），框架已支持用指定模型跑子智能体。

### 1.5 "上下文腐坏"——累积的工具错误污染后续决策

- **来源：** 同上 Cursor《持续改进我们的智能体框架》
- **问题：** 工具调用错误即使被 agent 自行纠正，错误仍留在上下文里，浪费 token 并导致"上下文腐坏"——累积错误降低模型后续决策质量，有时让 agent 卡住或完全失控。
- **原因：** agent 用的工具是最易出缺陷的界面；错误留在上下文中持续干扰。
- **解决方法：** 按成因分类错误（`InvalidArguments`/`UnexpectedEnvironment` = 模型出错；`ProviderError` = 工具方服务中断；`UserAborted`/`Timeout`）；按"每个工具 × 每个模型"分别算基线做异常检测告警；未知错误率超阈值即告警；每周跑自动化 skill 教模型搜日志找新问题建工单。一次集中冲刺把意外工具错误降低了一个数量级。

### 1.6 规则文件的注意力衰减——agent.md 效力随会话变长递减

- **来源：** [Fabien Sanglard — My agent.md to improve LLM-assisted code quality](https://fabiensanglard.net/agent.md/index.html) ｜ 2026-08-21
- **问题：** 把重复纠正（魔法数字、函数命名、注释习惯）沉淀进 agent.md 后代码质量显著提升，但会话拉长后规则效力衰减——模型对上下文中段指令注意力下降（[Lost in the Middle](https://arxiv.org/abs/2307.03172)），风格违规在长会话尾段重现。
- **原因：** 注意力对上下文位置不均匀，首尾强、中段弱；agent.md 注入后随会话增长逐渐"沉入"中段。
- **解决方法：** ① 一 feature 一会话，保持上下文短；② 观察到质量下降时显式说 "Reload agent.md" 强制重注入规则（确定性重载原文，非重新解释）；③ 让 agent 自己提案更新 agent.md（省去手动编辑），但作者强调这不是免读代码的魔法弹——LLM 持续幻觉不可信任，验证重心从代码风格转移到架构设计。
- **映射：** 标准 §1.9 规则文件的注意力衰减与维护。

### 1.7 单体 AGENTS.md 立即失败——0 行手写代码的百万行产品靠"地图 + 渐进披露"

- **来源：** [OpenAI — Harness engineering: a case study of Codex-built Symphony](https://openai.com/index/harness-engineering/) ｜ 约 2026-02
- **问题：** OpenAI 用 Codex 5 个月建成内部产品（3-7 名工程师、~1500 个 PR、约 1/10 传统工期、几乎 0 行人写代码）。最初把所有规则塞进一个巨大的单体 AGENTS.md：挤占任务上下文、让一切显得同等重要、迅速腐烂、还难以验证规则是否被遵守。
- **原因：** 规则文件不是越多越安全；常驻上下文的每条规则都在与任务本身竞争注意力，且无版本化维护机制的规则集必然过时。
- **解决方法：** ① 把 AGENTS.md 压到 ~100 行，只当**目录（map）**用，指向结构化 docs/ 按需读取（渐进披露）——"给 Codex 一张地图，而不是一千页手册"；② 建立 **golden principles**：机械化的口味规则（共享工具包优于手写 helper；禁止 YOLO 式探测数据，必须验证边界或用类型化 SDK）；③ **后台 Codex 任务**定期扫描代码库偏差、更新质量评分、开重构 PR，多数一分钟内可审自动合并；④ 加 **doc-gardening agent** 专门清理过时文档。最终瓶颈转移到**人类 QA 产能**——应对方式是把 UI、日志、指标做成 Codex 直接可读。
- **映射：** 标准 §1.8 规则编译与渐进披露、§2.3 Context Budget、§1.9 规则文件维护。

### 1.8 注意力稀释 70/20/10——"换大模型两周不如上下文管理一周"（阿里企业级平台演进）

- **来源：** [阿里妹（千问AI平台）— 从 Prompt 到 Harness：企业级 Agent 工程的完整演进之路](https://mp.weixin.qq.com/s?__biz=MzIzOTU0NTQ0MA==&mid=2247561689&idx=1&sn=bb7d379ffd983081f81048e4813d524b) ｜ 2026-08
- **问题：** 同一 Skill 3 步质量很好、8 步明显下降、15 步几乎不可用；换更大模型无改善。逐步骤 dump 上下文发现真相：到第 8 步时上下文中 **70% 是前几步工具调用的原始 JSON 返回、20% 是历史对话、只有 10% 是当前步骤的有用指令**——物理容量 128K 不等于有效容量，塞满 70% 噪音的 128K 不如精心管理的 32K。且是自我恶化循环：膨胀 → 稀释 → 参数错误率升 → 更多重试消息 → 进一步膨胀。
- **关键实证：** 团队曾花两周评估更大参数的模型，指标没变；上下文管理做一周，指标提升 40%。**"不要用更大的模型掩盖工程层面的问题"**——Agent 表现下降时先看上下文质量再考虑换模型。
- **解决方法：** ① **四层上下文防线按数据膨胀的时间顺序逐层拦截**：L1 工具结果外置（>8000 字符 / >10 元素数组强制存外部、上下文只留 refId+有界摘要，从根本消除 LLM 搬运大数组时"无意识摘要"造成的数据丢失）；L2 语义压缩（LLM 提取关键信息上限 2000 字符，失败降级为结构化截断+`__fallbackTruncated` 标记而非裸截断）；L3 对话压缩（85% 触发压到 30%——95% 触发可能没输出空间、50% 目标太保守压缩刚结束就再触发；交接文档用固定 schema，含**"已放弃的路径"独立字段**直接防重蹈覆辙、保留具体 ID/数值禁止概括泛化）；L4 DataBus 声明式依赖预取（按 step.input 声明预载，分 outline/search/context 检查模式，每步只取最小必要信息）。② **单一表示原则**：同一数据在任一后续 step 的 prompt 中只允许一种形态（小数据 inline 完整对象 / 大数据 artifact_ref，互斥不共存）——多形态共存会让模型花大量 token 交叉验证甚至因措辞差异产生幻觉；在 PromptBuilder 中做"编译时"检查，检测到同一 refId 多形态直接拒绝组装。③ **数据搬运谬误的解法是 parameterBindings**：LLM 搬运 UUID 会截断/混淆/幻觉，跨步骤数据传递改为运行时系统直接从上下文注入，跳过模型搬运环节——"让 LLM 做理解意图的事，让系统做精确传递的事"。④ **从防御到赋能**：五层修复管道 500 行代码（占执行逻辑 50%）换成声明式绑定 + step_control 显式表达（complete/skip/need_info）+ working_memory 模型自主记录 + Action Space 动态裁剪；迁移顺序是可观测性先行 → 声明式替代命令式 → 赋予模型表达和记忆能力。效果：Token 消耗降 60%+，30+ 步任务质量不再随步骤数退化。
- **细节教训：** LLM 重写 preview 会改变字段名和前缀导致前缀匹配恢复失败、脏数据流入下游——preview 必须用原始文本 substring 不经 LLM（"过度智能反而有害"，数据管道中确定性永远优先于智能性）。
- **映射：** 标准 §2.2 上下文分层、§2.3 Context Budget、§2 工具结果管理规则（单一表示、强制外置阈值）、§1.2 复杂度阶梯。

### 1.9 Harness 不是默认有益——同一任务 10 组配对实验：前沿模型加 harness 多花 7 倍成本、验收通过率零提升

- **来源：** [Naresh Jain（Specmatic / ConfEngine 创始人）— Are Harnesses Worth the Cost?](https://martinfowler.com/articles/are-harnesses-worth-the-cost.html) ｜ 2026-10-13（martinfowler.com）
- **问题：** 业界默认"给 agent 加 harness（行为约束 + 传感器）会帮它做对事、还能省 token"，但很少有人量化这个假设。作者用同一个 Java BFF（产品发现服务）做对照实验：每个模型跑 10 组配对，用 178 条外部验收测试判定，一组加 harness 一组不加。
- **实测数据（10 组平均）：** **GPT-6 Sol（前沿）** 加 harness 后 token 1133 万 vs 不加的 108 万（**10.5 倍**）、耗时 19 分 53 秒 vs 6 分 51 秒（约 3 倍）、成本 $2.679 vs $0.406（约 **7 倍**），而验收通过率**两边都是 10/10**——harness 没有换来任何验收收益。**GPT-6 Luna（成本优化档）** 不加 harness 只有 3/10 通过；加上 harness 后 10/10，单次成本 $0.273——**比不加 harness 的前沿模型还便宜三分之一，可靠性相同**。
- **原因：** harness 的价值取决于**介入时机**，而不是有无。弱模型缺的是"边做边校验"的能力，传感器在开发过程中持续运行确实把 3/10 拉到 10/10；前沿模型本来就一次做对，同样的传感器在开发过程中反复运行只是重复劳动。Luna 不加 harness 的失败集中在协议边界这类容易漏的细节上（202 异步流程、缺监控链接、Kafka `__TypeId__` header、`"categories": null`、错误码返回 415 而要求 400）——这类失败恰好是传感器能确定性拦住的。
- **解决方法：** 按模型能力分档决定 harness 介入时机——**弱模型（成本优化档）在开发过程中全程跑传感器；前沿模型把同样的传感器降级为最后一道独立门禁，跑一次即可**。作者原本的假设是"harness 能帮 agent 第一次就做对"，实测被直接推翻。
- **诚实披露的边界：** 10 组配对、单一 greenfield Java 服务、双方都用低 reasoning effort，样本量不足以支撑长期可靠性结论；需求书写得异常详细，未测试模糊需求、遗留代码、其他语言和开放权重模型；成本口径未计入 harness 与契约本身的编写维护成本，也未计入返工；harness 把指南与传感器打包在一起，无法分离各自贡献。
- **映射：** 标准 §1.2 Harness 设计（harness 不是默认有益、按模型能力与任务难度决定介入时机与频次）。

### 1.10 系统提示砍 66%、工具按需加载——token 效率的七项手段与两条反直觉

- **来源：** [Cursor（Jediah Katz, Connor O'Keefe, Calvin Yee）— Improved token efficiency for longer agent runs](https://cursor.com/blog/improved-token-efficiency) ｜ 2026-09-23
- **问题：** agent 运行时间越长、携带上下文越多，**上下文的反复组装**就成了主要成本。实测发现：即使在不到 20% 的对话里才会用到的工具，也在每一轮被完整加载；系统提示与工具定义已经成为最可控的一项成本。
- **七项手段：**
  - **系统提示瘦身约 66%**——模型变强后，大量"手把手"的指令已经不再必要，简单的工具定义它就能跟得上，旧指令只是在缩小搜索空间。
  - **工具动态加载**——把内置工具从常驻上下文中移出（此前已对 MCP 工具这么做过），只保留高频的读/搜/改/执行类工具，加上两类例外：模型会凭空幻觉调用的询问工具，以及流程关键工具（如创建计划）。
  - **缓存断点前移**——在稳定层之后显式标注缓存断点，把易变内容（如会话初始化）挪进一条"幽灵用户消息"，避免它污染前面的稳定前缀。
  - **文件读取压缩**——行号从"每行都标"改为"每十行标一次"。
  - **子 agent 提示收敛**——删掉"鼓励用子 agent 去探索"的引导提示，模型切换权限收回到用户与 harness 手中。
- **实测收益：** token 成本降 **7%** 且质量无损；涉及 MCP 工具的会话 token 降 **46.9%**；常驻工具描述 token 降 **60%**；冷缓存未命中次数降 20%；缓存读取 token 降 1.6%。
- **两条反直觉：** ① 子 agent 的上下文隔离不是免费的，它带来**协调税**——重复劳动、重复探索，省下的上下文要用额外的协调轮次换；② **只在评测集上优化不够**——评测集偏向难题，真实流量里大量是简单请求，两者的成本结构完全不同，必须上真实流量做 A/B 才算数。
- **映射：** 标准 §2.3 Context Budget、§2.10 上下文成本与稳定前缀、§9.6 成本可观测；与 §1.9（harness 的时机）、§8.6（本地指标陷阱）互补——三条共同说明"上下文里的东西都要问一句它值不值"。

### 1.11 高频上下文决策交给窄任务专用小模型——摘要/压缩/抽取不必用前沿模型

- **来源：** [LangChain（Sydney Runkle, Srimanth Tangedipalli, Neal Patel）— Building Long-Running Agents with ScaleDown and Deep Agents](https://www.langchain.com/blog/building-long-running-agents-with-scaledown-and-deep-agents) ｜ 2026-10-13
- **问题：** 长跑 agent 一直在做同一类上下文决策：什么时候压缩历史、怎么缩小过大的工具输出、怎么从长输入里抽出结构化字段。这些决策过去都交给前沿模型，而长跑 agent 的调用量让它们"又慢又贵"。
- **原因：** 这些任务的输出空间是**受限**的——只需要给出一个标签或一段原文片段，不需要开放式生成。用通用大模型做受限任务，等于用最贵的算力买它最不需要的能力。
- **解决方法：** 用**约束解码模型**（CDM，为单一窄任务训练、只返回允许答案）承担这些步骤，架构上保持分工：**agent 主模型负责跑循环，专用小模型负责循环周边的上下文工作**，通过中间件挂进 agent loop（摘要中间件替换历史、压缩中间件按查询裁剪工具结果、抽取中间件把字段写进 agent state）。三条配套纪律：压缩结果要**附带说明**，让模型知道可以不带压缩参数重新调用取回完整输出；专用模型调用失败时**保持历史原样、agent 继续跑**（不因辅助环节失败中断主链路）；**开放式生成仍留给通用模型**——写代码、起草回复、做规划不在专用模型的能力范围。
- **量化（厂商自报，需标注）：** CDM 在窄任务上比前沿模型快 **200 倍**、便宜 **467 倍**；在公开数据集上对比 GPT-5.5 / GPT-5.4 Mini / GPT-5.4 Nano 的平均值——摘要便宜 41 倍、快 2.7 倍，压缩便宜 138 倍、快 1.8 倍，且准确率更高。单条 trace 的文档压缩实测从 18,402 字符降到 3,110 字符（约 90%）。
- **边界：** 以上倍数均来自厂商自报，无独立评测；模型输入上限、文本/多模态支持范围都是当前实现值；无预置的漂移分类中间件，需要自行加断路器。
- **映射：** 标准 §2.3 Context Budget、§7.9 模型分层路由（受限任务专用模型 + 失败降级不阻塞主链路）。

### 1.12 先搭骨架、主 Agent 只读、看不懂就重做——五条反常识的 Agent 编程原则

- **来源：** [Carlos Kelkboom（首席架构师，Patrick Akil 播客）— AI 生成的代码看不懂就扔掉重来](https://mp.weixin.qq.com/s?__biz=MjM5MDE0Mjc4MA==&mid=2651295352&idx=1&sn=9ee14521ea3fad2bf13007ac2abec56f)（InfoQ 中文编译）｜ 2026-10-18；原播客 https://www.youtube.com/watch?v=mkN4uRZYPfs
- **问题：** Agent 让"启动项目"变得极容易，但跑上一两个月后往往越来越难推进：它变慢、产出越来越不符预期，原本的部署脚本被悄悄弃用并另外生成几个谁也说不清用途的脚本，同一个功能在代码库里被实现多次。等到想大改架构时，它往往选择继续打补丁而不是重构。
- **原因：** Agent 擅长沿一条路径快速求解，却不擅长把新代码放进整体结构里考虑；它也不考虑你将来想要什么，只把眼下的要求硬做出来。作者对此的表述是"它擅长写代码，但还不擅长从工程层面构建一个完整应用"。
- **做法（五条原则）：**
  1. **先亲自搭代码骨架**：建目录、文件、关键接口、类名与函数签名，甚至只写注释。作者通常花 20 分钟到一小时。目的是明确表达"我要怎样实现"，而不是让 agent 自己决定结构。
  2. **主 Agent 只读**：它负责对话、检索、确认意图，不改代码也不改文件系统；只有对"理解目标"的把握超过约 90% 时才建议启动执行 Agent。执行 Agent 可以跑 12 小时、可以并行多个。作者的触发点很具体：问 agent 一个关于创造力的演讲，它反问"要不要我把这个实现到你项目里"——那一刻他意识到它满脑子只想写代码，于是加了硬限制。
  3. **看不懂就扔掉重做**：执行结果隔离在 Git Worktree，跑一到两小时就暂停检查；打开代码找不到预期会出现的结构，直接丢弃重开，不花时间深挖。复盘时查清是骨架有问题、需求没说清、还是几个设计想法互相冲突，解决矛盾后再试，通常第二次即可。
  4. **尽量一次做大，而不是小步迭代**：Agent 擅长一次性完成较大任务，不擅长在存量代码上反复大改（连续开发基准得分显著偏低）。既然生成成本下降，就不必为保住已有代码而不断叠加补丁。
  5. **并行探索**：三个分支或 Worktree 各跑一个 agent，第四个 agent 横向比较，只合并各自最好的部分。
- **配套的检索习惯：** 先看某次提交的 diff 再看完整文件，把改动当作阅读前的热身；信息按"一句话摘要 + 路径/哈希/URL"分布存放，按相关性重排后逐层深入，不建图数据库——这本质上是一张可逐层检索的信息关系图。
- **审查看什么：** 除最终 diff，还看前期需求与架构决策、每次提交如何推进方案、实际增加了哪些复杂性。**PR 下的讨论不能消失**——作者反对"代码量太大所以没人读"的顺推，认为应当让 agent 少写一些、把每个功能做小、增加审查环节。
- **边界：** 单人多年实践与访谈观点，非对照实验；"三个 agent 并行 + 第四个评估"是其个人做法，未给量化结果。作者明确表示自己仍在摸索，并担心年轻工程师失去独立开发能力。
- **映射：** 标准 §1.2 骨架先行与执行主 Agent 只读（全节）、§12.4 隔离工作区与并行修改、§3.3 多 Agent 准入（并行探索）、§7.6 分层验证（看不懂即止损）。

### 1.13 一句话生成可投放页面——三种约束装配在同一棵 DOM 上

- **来源：** [巷年（大淘宝技术）— 告别 AI Demo 页面：构建支持淘内货品运营、可 C 端投放的会场 Agent Harness](https://mp.weixin.qq.com/s?__biz=MzAxNDEwNjk5OQ==&mid=2650546485&idx=1&sn=b679cea45f2b32788e0c3eb2d3568cac) ｜ 2026-10-19
- **问题：** "一句话生成页面"已经不稀奇，但生成的 HTML 几乎都不能上线：无法支撑端内渲染体系（性能、埋点、商品数据动态渲染都不符合要求）、无法做真实的供给挖掘与货品运营（AI 会编造商品数据，给了真实数据也不会处理个性化推荐、白底图/场景图、定坑/补利益点等诉求）、视觉样式不符合设计规范。
- **核心判断：** 一份 HTML 同时承载三项约束，三者性质不同，**不能合并成同一层级**：
  - **视觉设计是软约束**：视觉与风格 Skill 守住气质、视觉层级和关键特征，但相框、字体、层叠、留白仍可自由组合——让模型把设计做好，而不是照模板填空。
  - **货品数据是认知约束**：建立选品、Slot 与召回的认知，字段协议规定内容如何进入页面；AI 要分清哪些内容随页面保留、哪些来自商品字段。
  - **生码是硬约束**：协议规定 Section、卡片、字段的表达与装配边界；外观自由，但节点归属、字段位置、动态组件输入必须明确。
- **冲突的具体来源（本条最有价值的技术细节）：** 同一棵 DOM 被三种方式解释——视觉看结构与盒模型、数据链路识别 Slot 与字段承载节点、转码链路提取楼层与组件关系。由此产生三个陷阱：**视觉分组 ≠ 供给分组**（同楼层可混排不同 Slot，同 Slot 卡片可跨行、异样式）；**加 wrapper 会改变布局前提**（为 Slot 包一层容器，Grid/Flex 的直接子项就变了，跨行跨列与位置选择器受影响，`display: contents` 也会改变父子关系）；解法是**供给写进属性、布局保留层级**（把 Slot 与索引直接写在卡片元素上，运行时按属性定位并绑定字段，两种分组分别表达）。
- **二次编辑要先判影响面：** 运营的修改诉求分三个方向——改视觉、改供给（真正的选品与召回链路）、改数据投放（哪个坑用哪套供给），混合诉求按依赖顺序处理，最后回到同一份页面校验三类认知是否仍然一致：新供给能被现有卡片承载、新呈现保住字段替换与转码边界、新投放规则落到真实 Slot 与目标卡片的映射。
- **Skill 正文的压缩恢复（可迁移）：** 设计风格这类规则要在长链路里持续生效，难点是任务目标会变化（设计阶段追表现力、数据阶段关注供给、构建阶段关注协议）。做法是：先把视觉创作独立完成并存成产物，再进入供给与构建；**把加载的 Skill 正文包装成带名称的专门消息并独立持久化**——普通轮次沿用历史，微压缩不把它当普通读取结果清理；历史重建或完整压缩后，按加载记录和预算重新恢复正文，超长时保留截断与补读提示。否则压缩后只剩一句风格摘要。
- **prompt 缓存的四类未命中（实测归纳）：** 同轮对话中全量压缩会造成一次整体未命中；子 Agent 空上下文启动会重建缓存，执行超过 5 分钟也会让主 Agent 未命中；跨轮追问在 5 分钟内关键是消息恢复机制一致，5 分钟后缓存必然未命中，此时反而适合做微压缩（清掉不重要的工具结果）。判断：**缓存命中率低未必是上下文工程的问题**——对话周期长、用户隔很久才回来、窗口只有 200k 经常触发全量压缩，都会拉低命中率。
- **子 Agent 交接的三条失败与对策：** ① 只交回结论没交齐依据（选品子 Agent 只回"已创建选品集"，主 Agent 不知道哪些商品因价格或敏感肌限制被排除，下一轮把做过的判断再猜一遍）；② 追问时不知道谁掌握依据，主 Agent 得先定位原任务、找到排除依据，再决定自己处理还是恢复子 Agent；③ 上下文各自独立但修改汇入同一份会场，设计侧改了卡片结构、绑定侧基于旧节点修改，两份局部结果合并可能错绑或覆盖——**继承上下文、保留会话、共享工作区都不能代替当前版本核对、明确写入范围与统一验收**。对策是交接用"结论 + 执行记录归档地址"，过程保留为可重读的依据。
- **质检的取舍：** 质检工具要同时满足确定性高与检测速度快，但**不能阻碍创造力**——若为减少错误把生成限制成几套模板，设计创造力会一并消失。具体做法：先判布局条件（掉坑检查先确认共同父容器，区分显式缺格与末行不满）；倾斜卡片用变换前的原始宽度判断而非视觉宽度；遮挡用采样加元素命中检测，外部浮层作 warning 交截图复核；**允许设计不等于豁免重叠**（商品卡超阈值重叠仍报 error），而 Bento、旋转、横向滚动等合法反例需持续回归，否则模型会被错误规则逼成同一版式。
- **观测分层：** 从会话下钻到用户轮次，再看主/子 Agent 的请求与工具步骤；Provider 出口要记录 SDK 最终发送的请求与实际收到的响应——只有这样才能确认规则是否加载、图片是否进入请求、字段是否可见、工具结果以什么形式进入上下文。
- **边界：** 单团队生产实践，未给出量化收益（只说"很多页面已投放上线"与增量 GMV 持续正向）；部分机制（OSS 工作区、内部协议名）绑定其技术栈。
- **映射：** 标准 §2.4 上下文压缩（Skill 正文的专门恢复路径）、§2.10 上下文成本与稳定前缀（缓存未命中的四类归因）、§3.4.1 长期指令退出条件（规则随会话延续与恢复）、§7.6 分层验证（质检的合法反例回归）、§2.8 阶段上下文包与交接产物（结论 + 记录地址）；与 1.12（骨架先行）互补——那条讲人怎么定结构，本条讲结构如何用协议固化下来。

### 1.14 规则从 500 行涨到 800 行，AI 反而更不听话——改成"每步只看到该看的"

- **来源：** [刘俊毅（腾讯云开发者）— 给 AI 写了 800 行规则，它反而更不听话了](https://mp.weixin.qq.com/s?__biz=MzI2NDU4OTExOQ==&mid=2247697801&idx=1&sn=3a7b94e654b48a3d06627ebd265ab14e) ｜ 2026-10-21
- **问题：** 一个中等复杂度需求从评审到可体验版本原本要一个月，用了 AI 后压到一到两周、编码环节从以天计压到一两小时——但卡点不在模型能力：会话一长就忘约定、换会话重踩旧坑、需求转述几次就走样、报错日志要人一段段贴。最初的解法是写一个流程 Skill 把步骤列成清单，AI 总忘步漏步，于是不断加规则，**不到一个月从五百多行涨到八百多行，开头还加了五条"违反任何一条即为失败"的铁律**。结果规则越多 AI 越不听话。
- **原因（本条核心判断）：** **上下文里塞进的东西越多，每条规则分到的注意力就越少，最要紧的那几条反而被埋掉了。** 早期那份八百多行的 Skill，AI 每一步都要背着全部规则走。
- **做法（流程、知识库、工具三根支柱）：**
  - **流程按阶段切片**：17 个阶段分 7 组，每组一个专职子 Agent；编排器本身不分析需求也不写代码，每阶段产出写成编号固定的文档，下游只读上游文档，进度记在一个状态文件里。**17 个阶段各有一份规则片段，进哪个阶段才加载哪一份**——现在每一步只看到当前阶段要守的那几条。HALT 节点设在每组阶段结束时，人确认后才进下一组；多仓库需求在协议锁定前再停一次。
  - **三层知识各管各的**：① **代码图谱**（函数/类/模块是节点，调用/引用/依赖是边，本地语法解析、毫秒级查询）回答"这个函数定义在哪、改了影响谁"；原则是**代码事实绝不手写进文档**——文档里写了"某函数在某文件"，一重构就过期，AI 读到过时信息比没读到更糟。② **模块文档只写"为什么"**：职责范围（含不负责什么）、设计决策与原因、交互约定、关键时序与状态流转、已知的坑；写语义保证不写函数签名，写约定不写文件清单。③ **记忆由 AI 自己捕获**：会话中留意用户纠正、反复尝试才解决的问题、用户主动告知的关键信息，整理成"原来怎么做 / 正确做法 / 为什么"。
  - **知识淘汰靠命中埋点**：借工具钩子注册"工具调用后"触发，每次读文件或文本搜索跑一个脚本，判断是否访问记忆或模块文档目录，从返回内容提取条目锚点并累加命中次数（同一条目一分钟内只计一次，脚本异常静默退出）。**一个刻意设计：把这两层排除在代码图谱之外，迫使 AI 只能通过读文件和文本搜索访问它们，埋点才生效。** 统计脚本输出命中排行与"僵尸条目"，定期审计时僵尸条目逐条复核——过时的删、有用但检索不到的补关键词、常命中的补充完善甚至晋升。
  - **记忆晋升链**：写入前先归类（模块专属进模块文档、跨模块通用进全局约定、协作经验进记忆、行为约束是规则、代码事实交给图谱）；一条记忆反复验证成稳定约定后晋升进文档，**原条目随即删除**；同类问题反复出现说明记忆没防住，才考虑升级为规则。**AI 只能提建议**——进化记录先进待审阅区，由负责人逐条决定升级为规则、沉淀为记忆还是拒绝。
  - **一个通用工具 + 一份手册**：编辑器内部上百个消息接口，若各包一个 MCP 工具，工具列表会极度膨胀、选错概率上升。做法反过来——**只暴露一个通用工具，参数只有三个（哪个模块、调哪个接口、传什么参数）**，"该调哪个、怎么调、哪些不能调"全写进配套 Skill（接口速查表、按风险分级的调用规则、常用操作标准步骤）。工具列表只多一个，约束放在 markdown 里，改规则不必改代码重发服务。
  - **三道闸防转述失真**：一个"批量收回上限 20"的需求，设计写对了，到任务拆分被概括成"一键全部收回"，实现照着做——每步单看都合理，结果与需求不符。对策是**每道关口回读原文而非相信上一手概括**：设计出口逐条核对数字上限/多选互斥/禁止项的语义，拆分出口要求任务描述引用设计章节，实现入口写代码前必须回读设计原文（任务描述只作索引，冲突时以设计为准并上报）。
  - **PRD 覆盖矩阵**：把 PRD 拆成功能点，每个标注出自哪一节、设计中落在哪个接口/类/字段；两项自检——PRD 每节都要有覆盖（不能漏），设计里每个接口/字段/事件都要能对应到功能点（不能多，多了就是 AI 自己加戏，退回澄清）。
- **量化/实证：** 规则从 500 多行涨到 800 多行后效果反而下降；一次全量审计把记忆从 **148 条精简到 24 条**（大部分不是丢弃而是找到更合适位置）；**13 条已落地进化记录里 10 条沉淀为记忆、只有 3 条升级为规则**；编码从以天计压到 1–2 小时，多数需求 1–2 周完成；AI 每完成一个任务评估上下文消耗，**超过七成主动暂停并保存进度**；三个多月迭代 15 个版本。
- **边界：** 单团队自述实践，无对照组；部分机制（Knot 平台 harness、Cocos MCP、内部仓库结构）绑定其技术栈；"编码压到 1–2 小时"是主观统计口径，未给出测量方法。
- **映射：** 标准 §2.3 Context Budget（注意力是有限预算，规则按阶段加载）、§2.9 分层上下文加载（17 份规则片段按阶段注入）、§5.7 知识资产分层（代码事实/模块文档/记忆/规则四类分开治理）、§5.9 知识生命周期（命中埋点驱动的淘汰与晋升）、§9.5 Harness 熵与规则债（规则越多越稀释，升级为规则要克制）；与 1.8（注意力稀释 70/20/10）同源——那条给出比例证据，本条给出"按阶段切片 + 用命中数据淘汰"的完整工程解法。

## 2. Tool 设计与调用

### 2.1 工具输出过大污染上下文 + 测试日志要让 agent 能 grep

- **来源：** [Anthropic — Building a C compiler with a team of parallel Claudes](https://www.anthropic.com/engineering/building-c-compiler) ｜ 2026-02-05
- **问题：** 长跑自主 agent 的测试 harness 如果打印几千字节无用输出，会污染 context window；agent 被丢进全新容器无上下文，要花大量时间 orient。
- **原因：** 测试 harness 是给 Claude 用的不是给人用的，但人常按自己习惯写测试。
- **解决方法：** 测试最多打印几行，重要信息写文件；日志要"机器可处理"——有错误就写 `ERROR` 并把原因放同一行让 grep 能找到；预计算汇总统计避免 agent 重复算；给 agent 维护大量 README 和 progress 文件，频繁更新当前状态帮它自己 orient；agent 有 "time blindness"——会傻跑几小时测试，harness 要少打印进度（避免污染上下文）并提供 `--fast` 跑 1%/10% 确定性随机采样（每 agent 确定性但跨 VM 随机，既覆盖全文件又能定位回归）。

### 2.2 Claude `pkill -9 bash` 自杀——无限循环 harness 的副作用

- **来源：** 同上《Building a C compiler with parallel Claudes》
- **问题：** 用 `while true; do claude ...; done` 的 Ralph-loop 让 Claude 永续工作，但有一次 Claude 不小心执行了 `pkill -9 bash`，把自己杀了，循环结束。
- **原因：** agent 在 `--dangerously-skip-permissions` 下有完全自由度，会执行破坏性命令。
- **解决方法：** 在容器里跑（非本机）；接受这是长跑 agent 的固有风险，靠测试和 CI 守住质量边界。作者强调"看到测试通过就以为搞定"是错觉，自主系统尤其如此。

### 2.3 超 150 个 skills 让前沿模型退化——Stripe Kai 的两段式加载

- **来源：** [LangChain — How Stripe built their Knowledge AI Platform on deep agents](https://www.langchain.com/blog/how-stripe-built-their-knowledge-ai-platform-on-deep-agents) ＆ [stripe.dev — Meet Stripe's Knowledge AI Platform](https://stripe.dev/blog/meet-stripes-knowledge-ai-platform) ｜ 2026-08-03
- **问题：** Stripe 企业级全员 Knowledge AI 平台 Kai（一周建成、83% 全员周活、单会话最高 932 轮）在 skills 规模化时撞墙：system prompt 里堆上 >150 个 skills 的描述后，即使前沿模型质量也开始退化（还有 frontmatter 1024 字符的硬限制）。
- **原因：** 全量 skill 描述常驻 system prompt 超出模型有效注意力预算；skill 数量与任务无关的描述都在稀释信号。
- **解决方法：** ① **两段式加载**：先让 LLM 从目录选择所需 skill，再由 skill 的 `allowedTools` 决定加载哪些工具；基础 skills（会话摘要、时间线等）仍固定注入；② 意外发现：当前规模下**纯 LLM 选择优于 RAG**，更大规模才需 RAG/classifier 预筛；③ sandbox 实现为**工具**而非 agent 执行环境，保持权限边界干净；④ deep agents 架构（subagents 做上下文隔离 + filesystem 做 durable memory）支撑长会话。
- **映射：** 标准 §2.3 Context Budget、§1.8 渐进披露、§4 替换边界（sandbox 工具化）。

### 2.4 工具与技能绑定——没读技能就调不到它的工具，中途加载不动缓存前缀

- **来源：** [LangChain（Sydney Runkle）— Revamping Skills in Deep Agents](https://www.langchain.com/blog/revamping-skills-in-deep-agents) ｜ 2026-10-07
- **问题：** 企业技能库长到数千个、跨团队共享后，两个缺口暴露出来：① 工具与技能之间没有绑定关系——agent **可以不读技能就直接调用它的工具**，也可以读了技能却仍要满世界找配套工具；② 长跑线程里新增、修改或删除技能后，必须重开线程才能生效。
- **原因：** 工具加载和技能加载是两条独立路径，缺少"先读技能、后得工具"的因果约束；而技能元数据只在会话启动时解析一次。
- **解决方法：** 三项改动。① **工具绑定到技能**：在技能前置元数据里声明包含哪些工具，改由技能中间件按需传入而非直接给 agent——没读技能就调用会失败为"未知工具"，补上因果约束。② **技能可固定（pinned）**：应用可在首次模型调用前就把指令载入，省掉一次"读文件"往返，让工作在第一次模型调用就开始而不是第二次。③ **技能可重载**：把技能元数据置空后重跑，长跑线程不必重开即可拾取新增/修改/删除的技能。缓存处理上有讲究——模型支持对话中途加工具时，**绑定工具放在新的系统消息里，让它上面的缓存前缀保持原样**；不支持该能力的模型则按原样追加。
- **反直觉取舍：** 重载会改动系统提示、使提示缓存失效，但作者认为可接受——厂商缓存本就"在几分钟到一小时无活动后过期"，空闲线程的缓存早已是冷的。另一处判据：**不固定技能时，模型不保证会加载正确的技能**；固定的代价是常驻上下文，换来的是可预测性。
- **边界：** 无基准数据与量化结果；对话中途加工具依赖厂商能力（Anthropic、OpenAI 支持），其他模型只能追加工具。
- **映射：** 标准 §14 Skills 规范（渐进披露三级、工具与技能绑定）、§2.10 上下文成本与稳定前缀（新系统消息保缓存前缀）。

### 2.5 让 agent 自己造工具，别把 agent 本身当工具用——"纯属浪费 token"

- **来源：** [Burke Holland（GitHub）— When chat is the wrong UI](https://github.blog/ai-and-ml/github-copilot/when-chat-is-the-wrong-ui/) ｜ 2026-09-24
- **问题：** 聊天成为 AI 的默认界面，是因为它最先出现且万能，而不是因为它适合每个任务。一旦用户已经知道自己要完成什么，继续用对话表达就是一种低效的往返。
- **原因：** 聊天的价值在于**意图未知时的兜底**——我们无法预判用户想干什么，所以给一个通用入口。但意图一旦明确，专用界面在表达效率、可重复性和双向交互上都优于逐句对话。
- **解决方法：** 让 agent **按需生成一个界面**（文中称为 canvas——在应用内运行、没有浏览器外壳、能与 agent 双向通信的完整应用），之后用户直接操作这个界面，不再靠对话驱动。实例包括：与 agent 对弈的四子棋、浏览与安装本地软件包的界面（这一项完全不涉及 AI）、带智能提示的 SQLite 查询界面、为博客写作复活的旧式编辑器、以及工作流自动化面板。作者的原话是：**让 agent 造出工具，让后续交互变得免费；把 agent 本身当作工具反复使用，是纯粹的 token 浪费。**
- **边界：** 这是观点与个人实践文，非对照实验；文中无成本或性能指标，只给了构建工时的量级——SQLite 界面可以一次成型，工作流面板花了接近一天。作者建议的 agent 工作流是研究 → 原型 → 计划 → 实现 → 迭代 → 收尾，多数步骤不需要人在场。
- **映射：** 标准 §16 项目应内置能力、§4.9 CLI 与工具选择（能一次执行完的流程不要让模型逐步控制）。

### 2.6 800 个 MCP 服务、5000 个工具之后——"发现不等于暴露"与跨服务检索的缺失

- **来源：** [Uber Engineering — Designing MCP Gateway: Uber's MCP Management Platform](https://www.uber.com/us/en/blog/designing-mcp-gateway/) ｜ 2026-10-01
- **问题：** 各部门各自接 MCP 导致基础设施重复、工具难发现、耦合紧密。平台化之后网关托管了 **800 多个 MCP 服务、5000 多个工具**，规模本身又带来新问题：上下文膨胀与成本失控。
- **原因：** MCP 协议**没有原生的跨服务搜索能力**——agent 必须事先知道服务地址和工具名才能调用，这在几个服务时没问题，到几千个工具时不可用（既装不下上下文，也选不准）。作者的原话是这些问题"在小规模下并不存在"。
- **解决方法：** 拆成控制面（注册表）与数据面（代理网关）两部分，网关把 MCP 调用翻译成 HTTP/gRPC/TChannel 请求再翻译回来，底层服务无需改动。四项关键设计：
  - **默认关闭**——核心原则是"**被发现不等于被暴露**"，服务拥有者必须审阅、批准，且配置变更可回滚。
  - **自动爬取生成工具描述**——分布式定时任务扫描接口定义注册表，解析 Protobuf/Thrift 结构，用 LLM 生成对 agent 友好的工具描述。
  - **渐进式发现**——提供"发现服务 → 发现工具 → 取工具结构 → 调用"的分步工具，避免一次性灌入全部工具定义。
  - **响应裁剪与结果外置**——类 GraphQL 的响应投影在运行时裁剪返回值；代码模式让 agent 把大结果写进文件而不是塞进上下文。
- **边界：** 工具级授权与 PII 脱敏是必备项而非可选项；跨服务检索的缺失是协议层限制，只能靠网关层补，不能指望 agent 自己记住几千个地址。
- **映射：** 标准 §11.3 MCP 成本与上下文边界（白名单、不默认暴露全部工具）、§4.6 Capability 与 Action Space（按步暴露相关能力）、§2.5 上下文数据生命周期（大结果外置）。

### 2.7 "agent 拥有决策，工具拥有执行"——模糊测试的三层架构与两套探针

- **来源：** [Antonio Morales（GitHub Security Lab）— AI-powered fuzzing with the GitHub Security Lab Taskflow Agent](https://github.blog/security/application-security/ai-powered-fuzzing-with-the-github-security-lab-taskflow-agent/) ｜ 2026-09-24
- **问题：** 持续模糊测试无法自我维持——即便长期运行的 OSS-Fuzz 项目仍会藏着严重缺陷，因为需要人不断盯覆盖率、为未覆盖的代码写测试骨架、人工分诊崩溃。作者的出发问题是：**有多少人工劳动可以交给 agent？**
- **解决方法：** 三层架构，边界写在设计里：shell 驱动串联各阶段，taskflow 的 YAML 负责给 agent 下指令，MCP 工具负责实际执行——**"LLM agent 拥有决策，MCP 工具拥有执行"**。四个可迁移的设计点：
  - **阶段之间只经数据库通信，不走内存**——状态存 SQLite，各阶段通过它交换信息，任何一步都能独立重跑。
  - **为两个不同目的构建两套探针**：一套带模糊测试插桩（引导模糊器用），一套用于覆盖率报告（给人看用）——**同一份插桩干不了这两个目的**，模糊器的边插桩对人类可读的覆盖率报告毫无用处。
  - **时间预算倍增**：从 30 秒起步逐级翻倍到 960 秒（约 32 分钟/目标），早期轮次便宜、后期轮次深入。
  - **平台期检测**：连续两轮覆盖率增长低于阈值（默认 1% 绝对行覆盖）就停止，不为无收益的轮次付费。
- **反直觉与边界：** 无容器隔离——taskflow 直接在宿主机上跑模糊器、编译器和由 LLM 选择的构建命令，因此只应在一次性、无特权的环境里运行；生成的补丁标记为"需人工审查"，作者明确说明 agent 的分析受限于模型理解、**它会出错**，结论定位是"给人类的一个准备充分的起点，而非最终结果"。
- **映射：** 标准 §4.1 Tool 是契约（决策与执行分离）、§5.3 可恢复 Workflow（阶段经持久状态通信）、§4.4 Tool 输出规则（按用途分别产出可读输出）；与 §1.2（agent 探索、人做减法）同源。

### 2.8 技能生态的第一份量化：0.04% 的技能占了 62% 的安装，近一半只被装过一次

- **来源：** [Vercel（Amelia Charles, Andrew Qu, Jonathan Hefner）— State of agent skills](https://vercel.com/blog/state-of-agent-skills) ｜ 2026-09-25（分析 skills.sh 注册表公开数据）
- **规模与增速：** 7 个月内累积 **100 万个技能、约 2.8 亿次安装**。作为对比，GitHub 到 100 万仓库用了 27 个月，App Store 到 100 万应用用了 63 个月，npm 到 100 万包用了 117 个月。
- **四条关键发现：**
  - **供给与需求错位**：供给偏技术（软件工程类约占上架量的 25%，技术类合计过半），但需求分散在各种工作类型上。
  - **极度集中**：**375 个技能（占 0.04%）吃掉了 62% 的安装量**，前 1.2% 占 94%；**近一半的技能只被安装过一次**。连安装量最高的技能也不到总量的 1%——作者的解释是技能在"各个任务内部竞争、跨任务累积"，所以每个任务都会有自己的赢家。
  - **可迁移性比垂直深耕更值钱**：跨行业的技能占已分类技能的 66%，却占安装量的 87.5%，**单个上架平均安装量是垂直技能的 3.6 倍**；只有八分之一的安装绑定到特定行业。
  - **供过于求的领域反而更难被采纳**：软件工程类安装量比平均低约 30%，教育/生产力类低 39%，研究类低 55%；而供给不足的领域高于平均——业务运营 +74%、写作与文档 +50%、云与基础设施 +42%。
- **元规律：** "人们正在用 agent 改进 agent"——安装量超过 10 万的技能中，**agent 工作流与自动化是最大的一类**。
- **边界（作者自述）：** 安装计数既非独立用户数也非独立选择；功能/行业分布描述的是已分类样本而非全量；数字后续可能修订。本报告由 skills.sh 的运营方发布，**属 vendor 自报数据**，无独立核验。
- **映射：** 标准 §14 Skills 规范（认知价值分层：稳定通用的公开技巧会被模型权重吸收，长期价值在需持续更新与真实权限的领域）、§5.7 知识资产分层。

### 2.9 把"合并多份材料"做成可核对流水线——生成与验证分离 + 原子声明 + 三态核对

- **来源：** [Toby Sutor（Elastic）— Trust, but verify: Atomic claim checking against LLM hallucinations](https://www.elastic.co/blog/atomic-claim-checking-against-llm-hallucinations) ｜ 2026-09-24
- **问题：** 知识库里有大量重复文章，需要合并。任务人人认可其价值，却积压了四年——因为认真合并一篇要一小时，枯燥且无人愿意做。而直接让模型"把两篇合并"会产出流畅但静默丢信息的版本：丢前置条件、版本约束漂移（"8.12+" 变成 "8.x"）、丢失注意事项、编造从未存在的参数。**最危险之处在于流畅本身就是陷阱**——90% 忠实的合并读起来和 100% 忠实的一样顺，审查者会略读过去；而一旦写入知识库并把原稿退役，错误就成了唯一版本，没有东西可以对照。
- **做法（可直接复用的四步）：**
  1. **生成与验证必须分成两次调用，禁止自证**——"让同一遍既合并又自评，等于让它一边写作业一边给自己打分"。一次生成要同时保证流畅与完整，两者相互竞争，流畅会赢。
  2. **生成阶段把技术载荷列为逐字保留项**：代码块、命令、配置片段、URL、版本号不得改写，只有散文可以重写；并把源材料当作**数据而非指令**（防注入）。输出契约强制三部分：合并结果 + 冲突清单（主题/各源怎么说/取了哪个/为什么）+ 省略清单（省了什么/为什么）——**让"沉默"不是一个可选项**。
  3. **每条源材料单独跑一次核对，且在新上下文里跑**：把多条源合成一次调用会诱发混淆，让只出现在其中一条里的声明被漏判。
  4. **把源拆成"原子声明"逐条判断三态**：原子声明是单个事实、步骤、取值、警告或指令，复合句要拆开。这一步把无法回答的"这次合并好不好"换成数百个可回答的是/否蕴含判断——后者是当前模型能可靠处理的粒度。三态为**存在 / 部分 / 缺失**，其中**"部分"价值最高**：它捕捉到"影响 8.x"与"影响 8.12.0 到 8.12.3"这类精度损失，纯二元判断看不见。
- **人工角色的改变：** 从"通读并判断好不好"变为"裁定标记行"——人只看被标为缺失或部分的行，工作量随**标记问题的数量**而非输出长度增长。单次审查从**一小时降到约五分钟**，积压四年的任务因此可以清掉。
- **边界与配套：** 先设一道"这些材料真的是重复的吗"的前置判断——部分所谓重复其实是相邻主题，本应各自保留；核对做成零基础设施的浏览器扩展、不改动既有数据流，否则不会被真正用起来；改写强度可调（轻改到完全重写）。
- **核心判据：** 可信是**架构属性而非模型属性**。幻觉是设计约束，要针对它设计（分离生成与验证、原子化、强制申报），而不是指望换个更强的模型解决。
- **映射：** 标准 §7.7 忠实性验证的原子声明法、§2.6 单一表示与结构化 Compaction、§10.3 不可信数据规则（源材料当数据不当指令）。

### 2.10 把 agent 沙箱从"部署配置"改成"运行时参数"——启动时间 4.05 秒降到 648 毫秒

- **来源：** [Cloudflare — Cloudflare Containers, rebuilt to scale agent sandboxes](https://blog.cloudflare.com/faster-agent-sandboxes/) ｜ 2026-09-30
- **问题：** 原有容器模型假设"应用部署"——镜像与算力在部署期固定、集中灰度。但 agent 的用法完全不同：**沙箱是按任务即时创建、要瞬间就绪、要能暂停与恢复**。旧模型下每种"镜像 × 实例类型"组合都是一个独立应用、各带一套命名空间与路由逻辑（一个 Node 沙箱和一个 Python 沙箱 = 两个应用 + 两次部署），启动还要先经全局控制面解析配置、找容量、协调放置，且任何变更都是全量发布——平台决定哪些实例被替换，"不管某个 agent 是否正在任务中间"。
- **做法（五条可迁移的改造）：**
  1. **镜像与实例类型改为运行时参数**：代码在启动容器时传入，而非部署期写死——"原本需要一次应用加一次部署的事，现在变成一个 if 语句"。
  2. **让调度入口直达控制器**：不再包一层包装类，把执行、出网请求拦截、镜像与实例选择、快照都挂到同一个控制器上。
  3. **放置决策从全局下移到调用点**：优先在同机找容量，其次同区；优先复用已持有该镜像或快照的主机。
  4. **复用预热资源而非从零启动**：保留可复用的已就绪实例、复用网络与文件系统初始化、批量执行、跳过首次命令不需要的服务。
  5. **基础镜像预先分发到候选主机**，避免让用户等待下载与解包。
- **量化结果（第三方基准，100 并发沙箱、客户端测得的可交互时间）：** 中位 **4.049 秒 → 648 毫秒（6.2 倍）**；p95 5.839 → 0.910 秒（6.4 倍）；p99 6.717 → 1.129 秒（5.9 倍）。自家初步压测：6 个区域 5.387 秒内启动 10 万个容器。
- **边界与代价：** 旧抽象类仅维护到 2026-12-31，既有部署继续运行但不再更新——**这是有意保留的迁移负担**；新能力只在原生写法下可用；快照能力仍是 beta，且"可分叉"意味着基线漂移需要自行管理（官方明确点名评测场景）。
- **映射：** 标准 §4.4 Tool 输出规则（沙箱作为工具能力、预热与放置策略）、§1.3 环境真实反馈、§5.4 Workspace 与 Sandbox 状态。

### 2.11 决策模型：输出受限结构而非生成文本——延迟降一半以上

- **来源：** [Cloudflare — Introducing Clef: our open-source decision models, and new RL fine-tuning platform](https://blog.cloudflare.com/clef-decision-models/) ｜ 2026-10-01
- **做法（三条设计）：**
  1. **输出空间受约束**：模型输出的是**带概率的受限结构**（枚举选项），而不是自由文本——"这个域名 95% 是时尚、85% 是电商、<1% 是钓鱼"。约束输出空间让推理可以变成"**预填充后并行打分**"的**非自回归**过程，省掉逐 token 生成。
  2. **校准用标签平滑交叉熵 + Brier 损失**，并用排序 LoRA 适配器；训练目标里给相邻序数选项部分分、给分布偏移加惩罚。
  3. **部署靠近调用点**（边缘 GPU）以压缩网络延迟——决策模型的价值一半在模型、一半在路径。
- **量化结果：** 一次"抓取 + 渲染 + 分类"的完整判断，决策模型 **2.2 秒** vs 对照模型 **4.7 秒**且只给出两个分类；中位延迟 **209.3ms vs 对照 524.1ms**；轻量版 38.8ms（但质量更低）。
- **诚实披露的短板（重要）：** **在四项基准里有一项显著落后**——CLINC150+OOS 66.77 vs 对照 89.27；在 PhishNChips 与 When2Call 上也输给对照。作者同时点明：微调是**用通用能力换领域准确率**，速度最快的版本（5.8ms）质量明显更低。
- **边界：** 官方博客发布、基准自报、无独立复现；仅在标注充足、任务边界清晰的场景适用。
- **映射：** 标准 §7.9 模型分层路由（受限输出空间、非自回归、完整对照含败项）、§2.3 Context Budget（高频决策下沉到廉价模型）。

### 2.12 模型能自我复制到什么程度——以及这对做 agent 的人意味着什么

- **来源：** [William Zhou, Daniel Freeman（Anthropic Frontier Red Team）— AI models may be capable of self-replicating without access to a datacenter](https://www.anthropic.com/research/self-replicating-ai) ｜ 2026-10-12
- **测出了什么（能力水位）：** 一个 26B 模型（Gemma4-26B-A4B）在 **15 台杂牌安卓电视盒子**（每台约 55 美元、4GB 内存）上跑分布式推理，速度 0.39 token/秒；一个前沿开源权重模型（GLM-5.2）在**防火墙内的 8 节点云 VPC** 上完成端到端自我复制——**5 次试验中 4 次铺满 8/8 节点，1 次 7/8**。其他被测模型在此任务上稳定失败。推理环境搭建这一子任务的**能力下限是 9B 级模型**（在 9 种硬件里的 8 种上成功）。
- **对做 agent 系统的人可用的四条：**
  1. **监控异常的多 GB 级载荷传输与设备间持续流量**——这是基于权重复制的特征信号。
  2. **收紧默认配置、消除未认证服务**（研究里 ADB 端口无认证，这一步是"被简化的"）：这类复制程序**不需要 root，在用户态运行**。
  3. **把隔离与通知流程当作预案准备**：带通知的清理流程 14 天清除 92% 感染，不带通知只有 74%。
  4. **用蜜罐捕获复制程序的 harness 与载荷**，以刻画其行为。
- **趋势判断（须按估计读）：** 若按 13.7 ECI/年 的趋势线（R² 0.95），达到该能力水平的小模型可能在**当年年底**出现。参照量级：某僵尸网络感染超 200 万台设备，等价规模可提供约 13.3 万个副本、约 8 万 token/秒（约相当于 40 张 H100）。
- **作者自陈的边界（不可忽略）：** 评测**刻意把网络利用环节做成平凡的**（无认证端口），因此是真实世界成功率的上界；ECI 只是复制能力的**代理指标**，时间估计粗糙；速度估计锚定单一类 IoT 硬件与单一历史僵尸网络；未测试 AI 僵尸网络的蓝队对抗行为。
- **映射：** 标准 §10.1 沙箱边界（默认收紧、消除未认证服务）、§9.1 默认可观测（异常流量监控）、§10.5 OWASP Agentic 风险类别（rogue agents、supply-chain）。

### 2.13 缓存只缓了固定指令，没缓"逐轮增长的历史"——一次运行 $36.21 降到 $0.47

- **来源：** [OpenAI — Better prompt caching for GPT-6](https://openai.com/index/better-prompt-caching-for-gpt-6) ｜ 2026-09-22；[Asana cuts model costs 76x in browser tests](https://openai.com/index/asana-browser-agent) ｜ 2026-10-09（**两篇均需用浏览器读，脚本请求返回 403**）
- **问题（Asana StackAI 浏览器 agent）：** 长跑 agent 每轮都在重发不断增长的浏览历史（页面文本与截图）。该 agent 缓存了固定指令与工具定义，**但没缓存增长的历史**，于是这部分每轮都按全价重算。更麻烦的是它几乎每一步都在丢旧截图、裁文本——**每次编辑都改变历史，所以只给历史加缓存也不会有效**；而那些被丢掉的旧信息可能导致 agent 重新访问已经读过的页面。
- **做法（三条改动 + 一个前提）：**
  1. **把历史纳入缓存范围**，不只缓固定前缀。
  2. **调大历史预算**（测试了 12 万与 48 万字符两档）。
  3. **截图批量清理而非每步清理**——最优策略是让截图累积到 20 张再回退到最近一张，使历史在两次清理之间保持字节级稳定。
  - **前提是代码得支持受控实验**：原代码不是为对照实验设计的，agent 先做快速试验确定哪些变量重要，再**重构代码让一套前后端并行支撑多条工作流、每条带自己的设置**，最后才做完整研究。
- **量化结果：** 144 次运行的研究（4 个模型 × 6 种缓存与截图策略 × 各 3 次，任务是给 32 本书各采集 6 个字段）。原生产配置在 Model B 上每次运行估算成本**至少 $36.21**（部分运行跑到步数上限未完成），优化后同模型降到 **$1.24（29 倍）**；换到另一模型的最优工作流为 **$0.47**，比原配置便宜 **76 倍**、快 **5 倍**（约 4 分钟/次）。人工估算需 1–2 个月的调研，agent 约一周完成。
- **另一篇的可迁移控制项（Better prompt caching）：** ① **工具变化不一定要删定义**——用允许列表控制哪些工具可调用、不需要工具时把工具选择设为 none，从而保住缓存前缀；新增指令追加到上下文末尾的新消息，而非改动前面的稳定段。② **推理档位可中途调整而不破坏缓存**（把档位作为可追加的配置项，请求级档位不动）。③ **预热已知上下文**（共享指令、工具定义、参考资料在用户提问前装载），把处理移出用户等待时间。④ **配缓存诊断**：能看出是"工具变了/模型变了/参数变了/输入变了"哪一种导致失效，并给出受影响 token 数。实测某团队借诊断把命中率提升几个百分点、成本降 20%，并对缓存异常中断设置告警。
- **边界：** 两篇均为厂商发布（含客户证言），量化来自官方自测；Asana 案例中的成本是"估算模型成本"而非账单金额。
- **映射：** 标准 §2.10 上下文成本与稳定前缀（历史纳入缓存、降裁剪频率、工具变更用允许列表、预热、诊断）、§7.6 受控实验需先重构代码、§9.6 成本可观测。

### 2.14 上下文管理的五种手段都指向同一件事：移出去但别删掉

- **来源：** [Jess Weng（LangChain）— Context Engineering: How Deep Agents Remember](https://www.langchain.com/blog/context-engineering-deep-agents-remember) ｜ 2026-10-14
- **问题：** 长跑 agent 把指令、工具结果、文件内容一路累积，最终远超上下文窗口能舒适承载的量；历史与噪音越多，准确率与推理质量越差（上下文腐坏）。单纯靠检索只能解决"信息进来的部分"，解决不了"已经在里面的部分"。
- **原因：** 上下文增长有两种形态：**尖峰**（单次超大工具结果、粘贴的长文本）与**缓升**（多轮累积的搜索结果、笔记、草稿）。只处理其中一种，另一种仍会撞上限。
- **做法（五类手段，全部按"移出但不删除"设计）：**
  1. **外置**：工具结果超过约 2 万 token 时写入文件，模型只看到首尾几行预览加路径；超长用户消息阈值抬到 5 万 token，同样落盘。需要细节时用读取工具分页取回。
  2. **摘要**：接近窗口上限（约 85%）时，把较早的消息压缩成一段摘要，**最近若干条逐字保留**，摘要放在它们之前；被摘要的原文写到会话历史文件，需要时可回读；下次压缩会把上一次的摘要一并纳入。
  3. **技能渐进披露**：任务知识按需加载，系统提示里只留名称与描述——十个技能的成本约等于十行描述。
  4. **子 agent 隔离噪音**：把注定嘈杂的工作（跨多个来源调研）放进独立上下文，只回结果；子任务通常窄而自足，可以跑更便宜的模型并并行。
  5. **长期记忆**：跨会话保留学到的东西，以普通文件形式存放在自己的存储里——因此换模型或换供应商后记忆仍然可用。
- **六条可迁移原则：** 大输入应当外置而非截断（截断有损、外置可回取）；压缩必须可恢复；任务知识按需加载；噪音工作应当隔离；记忆应当由自己持有；默认阈值必须可配置（一个任务的合适阈值很少适用于所有任务）。
- **实现结构：** 每种手段都是挂在 agent 循环特定点上的中间件（开始前、每次模型调用前后、每次工具调用前后），在该点读取并改写上下文；多数已内建，无需自行编写。
- **边界：** 厂商文档型文章，外置与摘要阈值为其框架默认值，属于可调参数而非普适标准；案例（竞品分析 agent）为示意。
- **映射：** 标准 §2.4 上下文压缩（可恢复、截断 vs 外置、尖峰与缓升、逐字保留最近消息、阈值可配）、§2.5 上下文数据生命周期（外置给预览加路径、长期记忆自持）、§2.9 分层上下文加载、§3.3 多 Agent 准入（子 agent 隔离噪音）。
